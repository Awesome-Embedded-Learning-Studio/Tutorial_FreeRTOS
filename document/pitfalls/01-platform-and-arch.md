# 平台与架构:ARM64 segfault、GDB 信号、x86_64 前提

> 这一卷的第 1 篇。这一类坑不来自 FreeRTOS 内核,而来自 **POSIX port** 的实现细节——它把任务切换和调度同步这件事交给了宿主机的一段汇编和一组信号,而这两样东西都有平台假设。两条坑分别是 10 大陷阱里的「ARM64 segfault」(#5)和「GDB 信号干扰」(#7),它们都决定你能不能把这套模拟器用起来,所以放最前面。下一篇 [调度与同步](./02-scheduling-and-sync.md) 讲「分时 OS 当 RTOS 跑」带来的一类更深的坑。

## 为什么这一类坑和 FreeRTOS 内核无关

在展开具体坑之前,先把这一类坑的「归属」讲死,免得你以后误判。FreeRTOS 内核本身(tasks.c、queue.c 那一套)是跨平台的——同一份内核代码,跑在 STM32 的真 MCU port 上、跑在 ESP32 的 port 上、跑在 POSIX port 上,内核逻辑完全一致。但**内核要能跑起来,得靠一份和 CPU 架构强相关的 port**:任务切换要改寄存器、关中断要动 CPU 状态字、这些底层操作只能靠具体架构的汇编去干,所以官方为每类平台各提供一份 port。POSIX port 就是其中很特殊的一份——它不针对任何 MCU,而是针对符合 POSIX 标准的操作系统(你的 Linux、macOS、WSL2)。

POSIX port 干的事情是:把每个 FreeRTOS 任务映射成宿主机上一个 pthread,把 FreeRTOS 那套由硬件定时器驱动的 tick 换成一个软件定时器周期触发,把任务之间「触发一次上下文切换」这件事用一组信号(`SIGUSR1`、`SIG34` 这类实时信号)在 pthread 之间同步。这里有两个动作带着平台假设——**任务切换那一下要篡改线程上下文,这靠一段架构相关的汇编**,而这段汇编**只适配了 x86_64**;**调度同步靠 POSIX 信号**,而信号天然会被调试器截获。这两条平台假设,就分别种下了下面这两条坑。记住这个归属:出了 segfault 或被信号刷屏,别去翻 FreeRTOS 内核源码,也别说「FreeRTOS 不支持 ARM」——这是 **port 的限制**,换 port 就消失。

## ARM64 segfault:POSIX port 的架构天花板

**现象**是这一类里最唬人的:你在 aarch64 的机器上把 demo 编译出来(编译阶段一点事没有,gcc 本身认 aarch64),然后 `./posix_demo` 一启动就 segfault,经常连 `main` 都进不去,栈回溯里看不到任何有意义的 FreeRTOS 符号,全是宿主 glibc / libpthread 的内部地址。新手的第一反应往往是「我哪里写错了」或者「是不是 git submodule 没拉干净」,反复重新 clone 都修不好,因为它根本不是代码问题。

**为什么**会这样,根因就在上面那段上下文切换汇编。FreeRTOS 任务切换的本质,是把当前任务的寄存器现场保存起来、把下一个任务的寄存器现场恢复进去——这套「保存/恢复线程上下文」的操作,必须按 CPU 架构的寄存器布局、调用约定来写汇编,寄存器数量、压栈顺序、栈指针怎么动,x86_64 和 aarch64 完全不一样。POSIX port 只为 x86_64 写了这套汇编,在 aarch64 上它要么对着一组布局完全不同的寄存器乱动、要么跳进了不该跳的地址,进程当场崩。所以这不是「配置不对」「版本不对」,是 port 的**架构天花板**——那段汇编没有 aarch64 版本。

**对策**只有一条,也是诚实的:**换一个 x86_64 环境**。先确认架构:

```bash
uname -m            # 必须是 x86_64。若是 aarch64,这套 host 模拟对你关闭
```

如果是 aarch64,别去折腾「能不能让它跑起来」(改不动那段汇编),直接换环境:WSL 用户装一个 x86 的 Ubuntu 镜像而不是 ARM 版;Apple Silicon 用户用 UTM 跑一个 x86 的 Linux 虚拟机;台式机直接用 x86 主机。值得再强调一次:这个限制是 **POSIX port 的**,不是 FreeRTOS 内核的——同一份内核代码跑在 ARM 的真 MCU port(比如 STM32、ESP32、树莓派跑 FreeRTOS 的真 port)上毫无问题,所以千万别把它误读成「FreeRTOS 不支持 ARM」。这也正是我们[把教学目标限定在内核机制、把具体平台 port 声明为边界外](../tutorial/01_why-rtos/)的原因之一:host 模拟的价值在于让你快速理解调度与通信,而不是给你一个能上产的 ARM 运行时。命令行的搭建步骤全在[环境搭建章](../tutorial/02_environment/),这里只聚焦「为什么会有这条坑」。

**真硬件上怎样**:这条坑压根不存在。真 MCU port 是为你那颗芯片的架构专门写的,任务切换汇编、寄存器布局全是匹配的,不会有 segfault。所以这条坑是 host 模拟**独有**的「入场费」——你用它换来了零硬件门槛,代价是必须待在 x86_64 上。

## GDB 信号干扰:被 SIGUSR1 和 SIG34 刷屏

**现象**是第二条:你好不容易把 demo 跑起来了,想挂上 GDB 单步调试,结果发现自己根本走不动——每 `next` 一下都可能断在一个 `SIGUSR1` 或 `Real-time signal 0`(也就是 `SIG34`)上,GDB 打印一行 `Program received signal SIGUSR1`,然后停在那儿等你输入,你 continue 之后没两步又断在下一个信号上,根本没法正常单步、也没法专注看自己代码的执行。

**为什么**会这样,要回到 POSIX port 的调度同步机制。它把每个任务映射成一个 pthread,任务之间的上下文切换靠 `SIGUSR1`、`SIG34` 这一类信号在 pthread 之间同步——你可以理解为它**用信号来模拟 MCU 上「触发一次上下文切换」**这个动作。每次调度器要切任务,就给目标 pthread 发一个信号,那个 pthread 的信号处理函数里完成上下文保存/恢复。这套机制在正常运行时完全没问题(信号被静默处理、程序流畅跑),可你一旦挂上 GDB,调试器默认会把收到的每个信号都当成「值得停下来看看」的事件截获——于是那些本该被静默放行的调度信号,全成了打断你调试的噪音。

**对策**是进 GDB 之后立刻告诉它别理这几个信号:

```
handle SIGUSR1 SIG34 nostop noprint
```

两个开关的含义要分清:`nostop` 是「收到这个信号也别停下来」,`noprint` 是「收到也别打印通知」。两个一起设,这些调度信号就被彻底静默放行了,GDB 不再为它们停、也不再刷屏,你才能正常打断点、单步、看自己的代码。强烈建议把这条命令写进你的 `~/.gdbinit`,省得每次调试都手敲——POSIX port 的 demo 调试前它几乎是必过的第一关。顺带一个判别技巧:如果你看到 demo 运行时某些「看起来像崩溃」的信号中断,先确认是不是这两个调度信号,十有八九是 GDB 的误报,而不是你的任务真的炸了。

**真硬件上怎样**:这条坑也不存在,因为它的根因是「port 用信号模拟上下文切换」这个 host 特有的实现。真 MCU 上上下文切换是硬件/裸机汇编直接完成的,没有信号介入,自然也不会有调试器截获信号的问题。所以这条「调试前先 ignore 信号」的操作,只对 host 模拟有效;真硬件上用 GDB/J-Link/OpenOCD 调试时,该 ignore 的是别的东西(比如某些硬件断点异常),而不是 `SIGUSR1`。

## 小结

这两条坑是 host 模拟的「入场费」:一条要求你待在 x86_64 上(ARM64 一启动就崩,无解,只能换环境),一条要求你调试前 ignore 掉两个调度信号(否则被刷屏)。它们都来自 POSIX port 的平台假设,不是内核问题,所以对策也都是「绕过 port 的限制」而不是「改代码」。过了这两关,模拟器就能正常用了。下一篇 [调度与同步](./02-scheduling-and-sync.md) 我们进入更深的一类坑——它不来自 port 的平台细节,而来自「把一个分时 OS 当 RTOS 跑」这个根本张力:host 不实时、ISR API 会 hang、阻塞式 syscall 会拖垮模拟器、多核反而暴露竞态。

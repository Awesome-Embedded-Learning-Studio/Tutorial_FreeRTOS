# 资源与回收:栈溢出盲区、vTaskDelete、忙等饿死、CPU 占满

> 这一卷的第 3 篇,讲 10 大陷阱里的 #2(栈双重性)、#6(CPU 占满)、#10(vTaskDelete 上限)。这一类坑来自内核对 pthread 栈和线程生命周期管理的「够不着」——host port 把任务映射成 pthread,栈是宿主 glibc 管的、线程是宿主管的,内核想检测栈溢出够不着、想立刻回收删除任务的资源也卡在 pthread 的生命周期上。上一篇 [调度与同步](./02-scheduling-and-sync.md) 讲时序/并发模型的坑,最后一篇 [对照表](./04-primitive-behavior-diff.md) 把所有原语并列对照。

## 栈溢出检测:POSIX port 下的盲区

**现象**是最需要「诚实交代」的一条:你在[调试章](../tutorial/12_debugging/)学到 `configCHECK_FOR_STACK_OVERFLOW` 这个开关——设成 1 或 2,内核就会在任务切换时检查栈有没有溢出、溢出了调 `vApplicationStackOverflowHook` 报警。听起来很美好,你照着设了 2,然后故意写个深递归任务把栈撑爆——结果 hook **永远不触发**,程序也不因为爆栈而优雅停下。更扎心的是,你拿 `uxTaskGetStackHighWaterMark` 探这个任务的水位,预期看到水位随递归深度下降——结果**纹丝不动**,不管你递归多深,水位永远报同一个数。host 下栈溢出基本是个「盲区」,你看不见它发生。

**为什么**检测失效,根因在 POSIX port 对任务栈的实现。`configCHECK_FOR_STACK_OVERFLOW` 设成 2 时的机制是:内核在每个任务栈的栈底涂一段「魔数」(sentinel pattern,通常是 `0xa5a5a5a5`),每次任务切换检查这段魔数有没有被踩——被踩了就说明栈溢出过、踩进了哨兵区,调 hook 报警。这套机制的**核心前提**是:内核要能访问、能涂写、能检查「任务的栈内存」。在真 MCU port 上,任务栈是内核从堆里分出来的、内核拥有完整控制权的一块普通内存,涂魔数、检查魔数都没问题。但 POSIX port 把每个任务映射成一个 pthread,任务**真正的调用帧压在 pthread 自己的栈上**(由宿主 glibc 在 pthread 创建时分配和管理),而内核给任务准备的那块 `pxStack` 缓冲区,主要用来存 `Thread_t` 元数据 + 当个大小提示,**并不承接实际的函数调用帧**。

后果是双重的。第一,内核够不着 pthread 的栈去涂魔数,所以「任务切换时检查栈底魔数」这套检查要么被条件编译跳过、要么检查的是一个内核并不真正拥有的区域,自然检测不到溢出。第二,`uxTaskGetStackHighWaterMark` 靠扫 `pxStack` 缓冲区里「还没被踩的魔数」算剩余栈,但真实调用帧压在 pthread 栈上、根本不碰 `pxStack`,所以这个数几乎不随你的递归深度变化——它报的是 `pxStack` 那块「装饰性缓冲」的剩余,不是真实栈用量。而一旦 pthread 自己的栈真的被撑爆,宿主 OS 直接给进程发 `SIGSEGV`,程序崩在 glibc 层面、根本走不进你那个优雅的 hook。这套「双重失效」在[排错章的故障博物馆](../tutorial/13_troubleshooting/02-fault-museum.md)里有个场景专门演过——递归深度从 5 涨到 80,水位线始终是 16379 不动,我们老实演出「探针不可信」而不是伪造一个漂亮的递减数字糊弄读者。

**对策**要分场景。**host 模拟下**:认清这是盲区,别指望自动检测帮你兜底;靠**代码审查**估算每个任务的栈需求(有没有深递归?大局部数组?嵌套调用有多深?),给足 `usStackDepth`,外加 review;`uxTaskGetStackHighWaterMark` 在 host 上虽然不可信,但留着不碍事,真硬件上它会立刻变可信,所以模板里该有的实现都有。**真硬件上**:把 `configCHECK_FOR_STACK_OVERFLOW` 设成 2(方法二最严,既检查栈指针越界也检查魔数),开发期始终开着;同时 `uxTaskGetStackHighWaterMark` 在真硬件上是可信的(因为内核真拥有任务栈),定期打印各任务水位,把 `usStackDepth` 收紧到略大于峰值、省 RAM。这条坑还有一个 host 独有的「体量错觉」值得提:[03 内存章](../tutorial/03_memory/)讲过,host port 把每个任务栈强制到 `PTHREAD_STACK_MIN`(16384 字 × 8B = 128KB),真 MCU 上栈才几百到几千字——所以 host 上你「随手给个大栈」不会爆、真硬件上同样的 `usStackDepth` 可能就把 RAM 吃光了,移板前一定要按真硬件的栈量级重新核定。

**真硬件上怎样**:这条坑在真硬件上**整个反转**——检测生效、水位线可信、是 FreeRTOS 兜底排查栈问题的第一道防线。`configCHECK_FOR_STACK_OVERFLOW=2` + 周期性的 `uxTaskGetStackHighWaterMark` 是真 MCU 上的标配组合(被动 hook 兜底已发生的溢出、主动水位计平时监控趋势),只有 host 模拟下被动那条失效、我们靠主动那条和代码审查撑住。

## vTaskDelete 的资源回收差异

**现象**是生命周期管理时容易踩的:你用 `vTaskDelete` 删一个任务,直觉上「删了就没了、资源立刻归还」。在真 MCU 上这个直觉基本成立;但在 host 上你会注意到一些怪事——删完任务后立刻 `xPortGetFreeHeapSize`,free heap 没怎么涨(任务占的栈和 TCB 好像没马上还回来);或者你反复「建任务→删任务→建任务」,跑一段时间后 free heap 缓慢下降,像是删掉的任务有残留没释放干净。

**为什么**回收有延迟,根因在 FreeRTOS 的 `vTaskDelete` 实现和 pthread 的生命周期之间的张力。`vTaskDelete` 内部有个规定:**删除一个任务时,如果调用者就是被删任务自己**(`vTaskDelete(NULL)` 自删),它的栈和 TCB**不能立刻释放**——因为你正在用的就是这个栈,立刻 free 掉等于脚下拆台。所以内核的做法是:把被删任务标记成 `eDeleted` 状态、挂到一个「待回收列表」上,真正释放它的栈和 TCB 这件事,推迟到 **idle 任务**运行时由 idle 任务来干(idle 任务循环里有段「清理已删除任务」的逻辑)。这套「延迟回收」设计在 host 和真硬件上逻辑一致,但**延迟的程度**差很多。

在真 MCU 上,idle 任务很快就能被调度到(系统一闲就跑 idle),所以「删除→真正回收」的间隔很短,你几乎感觉不到。但在 host 上,事情被两重因素放大。第一,host 上每个任务占的栈大得离谱(128KB,见上一条),所以「待回收列表」上挂着的每个被删任务都压着一大块内存,空闲堆回收不及时的影响被放大了。第二,host 的 idle 任务要真正被调度到,前提是「没有更高优先级的任务 ready」——如果你的系统里有忙等的高优任务不让出 CPU,idle 根本跑不到,待回收的任务就一直挂着、内存一直不还。这就是为什么 host 上反复建删任务会看到 free heap 缓慢下降——不是泄漏(只要 idle 能跑到最终会还),是「回收被饿死」了。

**对策**有三层。**第一层,理解回收是异步的**:`vTaskDelete` 之后不要假设资源立刻归还,如果接下来要立刻 `xPortGetFreeHeapSize` 验证,先 `vTaskDelay` 几个 tick 让 idle 有机会跑、把待回收的清掉。**第二层,保证 idle 能跑到**:别让忙等的高优任务把 idle 饿死(见下一条),否则不光低优任务不跑、连已删任务的资源都回收不了——这条和 CPU 占满是同一根因的两面。**第三层,长期建删场景盯 free heap**:如果你的应用确实会反复建删任务(比如「按需起处理任务」的模式),周期性打印 `xPortGetMinimumEverFreeHeapSize`,确认回收最终在发生(长期看 free heap 不该持续单调下降);若真有泄漏(只建不删、或句柄丢了),那是 bug,要修。顺带一个相关点:`vTaskDelete` 删的是任务,但任务**用到的内核对象**(队列、信号量、事件组)不会自动释放——内核不追踪「哪个任务拥有哪些对象」,所以你 `vTaskDelete` 之后,那个任务建但没 `vQueueDelete` 的对象会永远挂在堆上,这是「对象泄漏」,host 和真硬件上都是 bug,都得自己管好配对。

**真硬件上怎样**:回收机制一样,但因为栈小(idle 很快跑到、待回收清得快),「延迟回收」几乎感觉不到,`vTaskDelete` 后资源基本立刻归还的直觉成立。但「对象不自动释放」「只建不删是泄漏」这两条 host 和真硬件完全一致——栈小只是让你「更晚才撞上泄漏」,不是没有泄漏。所以养成「建/删配对、对象生命周期和任务生命周期分开管」的习惯,跨平台都受用。

## CPU 占满与忙等饿死

**现象**是排错章里反复出现的经典:你有个高优先级任务,逻辑是「死循环里轮询某个状态、状态变了就处理」,循环里**没调任何会让出的 API**(没有 `vTaskDelay`、没有阻塞式的 `xQueueReceive`、没有 `taskYIELD`)。结果这个任务一上 CPU 就再也不撒手——因为它优先级最高、又从不阻塞,调度器永远没有理由切走它。后果是:所有优先级比它低的任务全被饿死(starvation)、一个都不跑;idle 任务跑不到(于是上面说的 vTaskDelete 待回收也清不掉);严重时连 tick hook、定时器服务任务这种靠系统调度的东西都受影响,整个系统像被这一个任务「卡死」。表现就是「我建了好几个任务,怎么只有最高优先级那个在打印,别的都像没启动」。

**为什么**会这样,是 FreeRTOS 抢占式调度的「阴暗面」。FreeRTOS 是**严格基于优先级**的:只要当前有 ready 任务,调度器永远选 ready 集合里优先级最高的那个去跑;一个任务**主动让出**(进 blocked/suspended 或调 `taskYIELD`)是其他同优先级或低优先级任务得以运行的**唯一**机会(抢占只能让更高优先级的任务插队,救不了低优)。所以一个高优任务如果从不阻塞,它就独占 CPU 到底,别人一点机会没有。这和「裸机 super-loop 里一个死循环占住」本质一样,只是 RTOS 给了你「阻塞式 API」这个让出的手段——你不用,就退化回 super-loop 了。

在 host 上这条坑还有个「加剧器」:host port 的 `vApplicationIdleHook` 模板里**故意放了个 `usleep`**([环境章](../tutorial/02_environment/)讲过 app_hooks.c 的样板)。为什么要这么干?因为如果 idle 任务也在那儿空转不让出 pthread,整个 FreeRTOS 进程会**把一个宿主 CPU 核 100% 占满**(top 里看到一个核拉满),既浪费电又可能触发宿主的温控降频、进一步加剧时序抖动(见[调度同步篇](./02-scheduling-and-sync.md)的非实时那条)。idle 里 `usleep` 一下,让 idle 主动把 pthread 让给宿主 OS,这个核就不至于 100% 空转。但注意:这只解决「idle 空转占核」,救不了「你的高优任务忙等把别人饿死」——后者得靠你自己让出。

**对策**是养成「高优任务必须让出 CPU」的铁律。**最直接的是用阻塞式 API 替代轮询**:与其「死循环里查队列有没有数据」,不如 `xQueueReceive(q, &item, portMAX_DELAY)`——队列空时任务自动进 blocked(不占 CPU)、有数据自动唤醒,这是 RTOS 的正确用法,既不饿死别人、又不浪费 CPU。**其次是必须轮询的话加让出**:逻辑上确实要轮询(比如查一个标志位),那就每次轮询后 `vTaskDelay(pdMS_TO_TICKS(1))` 睡一小会儿、或者 `taskYIELD()` 让出一次,给别人留窗口。**再次是核对优先级设计**:梳理一遍你的任务优先级,确认没有「高优任务忙等」的组合;[04 任务章](../tutorial/04_tasks/)和[08 资源管理章](../tutorial/08_resources/)都强调过「善用 blocked 让出是多任务并存的前提」。[12 调试章](../tutorial/12_debugging/)的运行时统计(`configGENERATE_RUN_TIME_STATS`)是定位这条坑的利器——如果某个任务 CPU 占用接近 100%、而它本不该这么忙,十有八九是在忙等,盯那个任务改。

**真硬件上怎样**:这条坑 host 和真硬件**完全一致**——抢占式调度的逻辑跨平台一样,高优任务忙等在任何 FreeRTOS 平台上都会饿死别人。区别只在于「后果的可见性」:真 MCU 上 CPU 100% 占满不一定有「top」给你看,你可能只观察到「低优任务不跑」;host 上你能 `top` 看到核被拉满、还有 idle 的 `usleep` 机制兜底。但「用阻塞式 API、别忙等、保证让出」这条纪律,host 上养成了、真硬件上照样受用,反而是 host 的观测手段让你更早学会它。

## 小结

这一类坑的共性是「内核对 pthread 栈和线程生命周期够不着」:栈溢出检测因为内核够不着 pthread 栈而失效(水位线也不可信,真硬件上反转)、vTaskDelete 的资源回收因为 idle 要跑到才能清、host 上栈大又容易被饿死而显得延迟(真硬件上几乎无感)、忙等饿死则跨平台一致但 host 上更容易观测。它们给你的教训是:**host 上对「栈」和「生命周期」这两类问题的诊断要打折扣,移板前按真硬件的栈量级重新核定、把代码审查当主要手段**。最后一篇 [对照表](./04-primitive-behavior-diff.md) 我们换个视角,把每条原语(队列、信号量、定时器、任务通知、事件组、内存)在 host 和真硬件上的行为并列摆出来,逐条核对预期。

# 调度与同步:非实时、ISR API hang、阻塞 syscall、多核竞态

> 这一卷的第 2 篇,讲 10 大陷阱里的 #1(非实时)、#3(ISR API hang)、#4(系统调用不安全)、#8(timing 需手动注入)、#9(多核新竞态)。这一类坑比[上一篇](./01-platform-and-arch.md)的平台细节更深——它的根因是「你把一个分时 OS(宿主 Linux)当成 RTOS 在跑」这个根本张力,所以好几条坑在真硬件上根本不存在、或者反过来。下一篇 [资源与回收](./03-resources-and-recovery.md) 讲栈、任务删除、CPU 占满。

## 非实时:timing jitter 不可信

**现象**是你一旦想在 host 上「量」任何和时间有关的东西就会撞上:你写了个任务,用 `vTaskDelay(pdMS_TO_TICKS(10))` 想让它每 10ms 跑一次,然后用 `xTaskGetTickCount()` 量两次之间的实际间隔,期望看到稳定在 10ms——结果它有时 9ms、有时 12ms、偶尔蹿到 30ms,抖动毫无规律。你以为是 tick 频率设错了,查了 `configTICK_RATE_HZ` 没问题;以为是任务太多被抢,关掉别的任务单独跑还是抖。更糟的是,你拿 host 上测出来的「某任务响应延迟 2ms」去推断真硬件「也是 2ms 量级」——这个推断是错的。

**为什么**会这样,要回到 POSIX port 的 tick 实现。它把 FreeRTOS 那套「由硬件定时器精确驱动的 tick」换成了一个**软件定时器**在宿主机上周期触发——这个软件定时器的精度受宿主 OS 调度器支配,而宿主 Linux 是个**分时操作系统**,不是 RTOS。分时系统的核心目标是「公平地让一堆进程共享 CPU」,不是「保证某个事件在确定的上界时间内发生」。于是你的 FreeRTOS 进程被宿主 OS 调度器随时挂起(等磁盘、等网络、被别的进程抢占、被 CPU 频率调节降频),tick 的触发时机就跟着抖,`vTaskDelay` 的实际睡眠时长也就抖。这和真硬件上「硬件定时器中断一到、内核就切任务」的确定性是两码事。说白了,**host 模拟下没有实时性可言**,这正是我们在[为什么需要 RTOS](../tutorial/01_why-rtos/)里把实时性、中断延迟、功耗明确划成边界外的原因。

**对策**不是「让它变实时」(变不了,宿主 OS 不答应),而是**调整你对 host 测试的预期和用法**。第一,host 上只验证「逻辑对不对、原语配合通不通」,不验证「延迟多少、抖动多少」——凡是带时间断言的测试(「必须 10ms 内响应」)在 host 上都不可靠,别写、也别信。第二,如果你想看「相对时序」(谁先谁后、A 在 B 之前完成),host 是可信的,因为内核调度逻辑一致、事件先后关系一致;要看「绝对时序」(具体延迟数值),只能上真硬件。第三,排查「是不是因为 host 抖动导致的现象」有个小技巧:把那段逻辑的延迟改成用 tick 数(`xTaskGetTickCount`)而非墙钟时间(`clock_gettime`)来度量,tick 数是内核自己的计数、不受宿主墙钟抖动影响,更能反映「内核视角下事件发生的先后」。

**真硬件上怎样**:真 MCU 上 tick 是硬件定时器驱动的,tick 周期由晶振和分频决定、极其稳定(微秒级抖动),`vTaskDelay` 的实际睡眠时长基本就是设定值。所以你在真硬件上测出来的延迟、抖动是可信的——这也是为什么「延迟上界」「中断响应时间」这些 RTOS 的硬指标,只能在真硬件上量、不能在 host 上量。

## ISR API hang:别从外部 pthread 直调 FromISR

**现象**是中断章那颗最大的雷:你学完「ISR give、任务 take」这套延迟中断处理的经典模式,想在 host 上自己搭一个「外部线程模拟中断源」——比如起一个独立的 pthread,在里面周期性地调 `xSemaphoreGiveFromISR` 给处理任务发信号。结果程序一跑就**卡死**:外部线程卡在某次 `GiveFromISR` 上再也回不来,处理任务也收不到信号,整个进程挂住,没崩溃、没断言、就是 hang,Ctrl-c 才能退,debug 起来极其折磨。

**为什么**会 hang,根因在 POSIX port 对「中断」这个概念的实现上。`*FromISR` 这套函数内部有一个隐含假设:**「我现在正处在一次被 port 正确跟踪的中断里」**——它会去碰 port 的中断嵌套计数、去发调度信号、去做「中断退出时该做的切换」。在真硬件上,ISR 是被硬件异步调进来的、port 完整跟踪了它的进出;在 host 上,port 只在它**自己管理的几个上下文**里跟踪中断(tick 中断、软件定时器回调所在的 daemon 任务上下文)。你在一个 port 根本不知道的 pthread 里直调 `GiveFromISR`,这个「中断嵌套计数」和「调度信号」就全乱套了——port 以为自己在处理中断、实际在一个野线程里,计数错乱、信号发飞,典型表现就是死锁在 give 上。详细的机制在[中断章概念页](../tutorial/07_interrupts/01-concepts.md)讲过,这里是它的「坑点」落地。

**对策**是**永远不要从外部 pthread 直调 FromISR**,改用一个 **port 跟踪的上下文**来扮演 ISR。最常用、最安全的两个落点是:**软件定时器回调**和 **tick hook**。软件定时器回调跑在内核自动建的「定时器服务任务」(daemon task)上下文里——它是个正经的 FreeRTOS 任务、被 port 正确管理;tick hook 跑在每次 tick 中断的处理里——POSIX port 把 tick 也实现成了一段被跟踪的中断路径。从这两个上下文里调 `*FromISR`,port 不会错乱、不会 hang。换句话说,host 模拟下我们让「软件定时器回调」或「tick hook」来**扮演真硬件上 ISR 的角色**:它们都满足 ISR 的核心特征——「被异步调进来、必须极快返回」——于是它们成了我们演练延迟中断处理的安全舞台。具体怎么用定时器回调当模拟中断源,在[中断章 demo](../tutorial/07_interrupts/02-deferred-isr-demo.md)里完整演过。

**真硬件上怎样**:这条坑消失,但「别用野线程」这条纪律依然有价值。真硬件上 ISR 是真正的硬件中断,你直接在 ISR 里调 `*FromISR` 就是正解,port 完整跟踪、不会 hang。但如果你在真硬件项目里也搞了个独立的 OS 线程(RTOS+Linux 混合系统常见)去碰 FreeRTOS 内核,同样的「野线程直调」问题会以另一种形式重现——所以「中断源要么是真 ISR、要么是 port 跟踪的上下文」这条规矩,跨平台都成立。

## 阻塞式 syscall 拖垮模拟器

**现象**是 host 模拟特有的、特别坑爹的一类:你某个任务里需要等一个「外部事件」——比如从标准输入读一行、等一个 socket 连接、`select` 一个文件描述符——于是你直接在那个 FreeRTOS 任务里调了 `fgets`、`read`、`accept`、`select` 这类**阻塞式系统调用**。结果这一个任务阻塞住的瞬间,整个模拟器卡住了:别的任务也不跑了、tick 也不走了、控制台一片死寂,像是 scheduler 被冻住了。你以为死锁了,查了半天锁没问题——根因根本不在 FreeRTOS 这层。

**为什么**会拖垮整个模拟器,要回到 POSIX port 怎么实现任务切换。它靠 `SIGUSR1`/`SIG34` 这类信号在 pthread 之间触发上下文切换,而信号是**异步送达**的——只有当目标 pthread 处于「可以被信号打断」的状态时,信号才能被处理、切换才能发生。当你在一个任务里调了阻塞式 syscall,那个 pthread 就钻进了**内核态的阻塞等待**(等 I/O、等 socket),这时候宿主 OS 给它发的信号默认会被「屏蔽到 syscall 返回之后」才处理(这是 Unix 信号的经典行为:慢系统调用被信号打断后会重启或返回 EINTR,但很多阻塞点并不返回)。结果是:这个 pthread 钻进内核态出不来,port 给它发的切换信号收不到,调度器卡在等它,整个系统的任务切换链条就断在这一环上。更隐蔽的是,有时它不会立刻冻死,而是任务时序变得极乱(信号延迟处理),现象是「偶尔卡、偶尔乱」,debug 到怀疑人生。

**对策**是**别在 FreeRTOS 任务里直接调阻塞式 syscall**,用以下几种安全替代。第一,**用带超时的轮询**:`select`/`poll` 配一个短超时(几毫秒),每次只短暂地探一下有没有 I/O、有就处理、没有就 `vTaskDelay` 让出 CPU 再探,绝不长时间钻进内核阻塞。第二,**把阻塞 I/O 隔离到一个独立的「桥接」线程**:起一个**不归 FreeRTOS 调度器管的普通 pthread** 专门做阻塞 I/O(`read`、`accept` 都放它那儿),它拿到数据后通过一个线程安全的手 notify 到 FreeRTOS 这边——但注意,跨线程通知 FreeRTOS 任务不能用 `*FromISR`(那是给 ISR 的,见上一条),得用 port 提供的 `vPortYield` 类机制或干脆用一个 FreeRTOS 任务轮询一个共享标志位。第三,**host 演示尽量回避真 I/O**:本教程所有 demo 的「输入」都用代码里硬编码的 Mock 数据周期注入(用 `vTaskDelay` 模拟采样间隔),根本不碰真 `read`/`accept`,这就是为什么我们的 demo 不会被这条坑咬到。

**真硬件上怎样**:真 MCU 上通常没有「阻塞式 syscall」这个概念——没有标准输入、没有 socket、`read` 这种东西根本不存在,IO 是直接读寄存器或经中断/DMA。所以这条坑是 host 模拟**独有**的、源于「宿主 OS 的阻塞语义和 port 的信号切换机制打架」。真硬件上你照样要避免「在任务里干长活不让出」(那是 starvation,见[下一篇](./03-resources-and-recovery.md)),但不会因为「syscall 阻塞」而冻死整个系统。

## 模拟中断源:timing 靠手动注入

**现象**不是「出错」,而是「缺料」:你学完中断章,想在 host 上看到一个「外部事件触发任务」的效果——但 host 上**根本没有真的中断源**。没有按键、没有串口硬件、没有 DMA 完成中断。你的处理任务在那儿 `xSemaphoreTake` 死等,可谁来 `Give`?如果你不主动安排一个「事件源」,那个信号量永远不会有人 give,处理任务永远不跑,程序像是没反应。

**为什么**要手动注入,根因就是上面反复说的:**POSIX port 没有真正的硬件中断**。真硬件上中断是物理事件触发的(按键的电平变化、定时器溢出、串口收到字节),CPU 硬件异步地把控制权交给 ISR;host 上没有任何物理事件可触发,所以「事件」必须由你的代码**周期性地、主动地**造出来。这其实是「无硬件模拟」的必然代价——你换来了零硬件门槛,代价是「现实世界那一侧」得你自己扮演。

**对策**是把上一条「ISR API hang」的对策和「事件源」的需求合起来:**用软件定时器回调或 tick hook 同时扮演两个角色——既是「安全的 ISR 上下文」、又是「周期事件源」**。最典型的写法是建一个周期定时器(`xTimerCreate` 配 `pdTRUE` 表示自动重装),回调里调 `xSemaphoreGiveFromISR` 给处理任务发信号,周期就是「模拟的事件到达频率」。这样处理任务 `xSemaphoreTake` 每次都能在定时器到期时被唤醒,完整复现了「中断 give、任务 take」的延迟中断处理模式。具体代码在[中断章 demo](../tutorial/07_interrupts/02-deferred-isr-demo.md)和[tick hook](../tutorial/07_interrupts/03-dashboard-button-irq.md)的 dashboard 增量里都有。还有个细节:模拟「按钮」这种**偶发**事件,用单次定时器(`pdFALSE`)或者让周期定时器里带个随机条件「偶尔 give」即可,不必真去读按键。

**真硬件上怎样**:这条「手动注入」的操作在真硬件上**反过来**——你不用造事件源,事件自己会来(按键中断、串口中断硬件会发)。你要做的只是写好 ISR(在 ISR 里 `GiveFromISR`),事件触发的时机由硬件决定。所以「定时器回调当 ISR」这套 host 写法搬到真硬件上,就是把「回调里的 GiveFromISR」换成「真 ISR 里的 GiveFromISR」,其余代码(处理任务的 take、延迟处理逻辑)**一行不用改**——这就是我们坚持用「port 跟踪的上下文」演中断的全部意义:模式是真的、可移植的。

## 多核新竞态:host 反而更容易暴露竞态

**现象**是这一类里最反直觉的:你在 host 上写了个多任务程序,跑着跑着偶发地崩了、或者数据偶发地错乱(计数器少了几次、队列里数据错位),你费劲复现、修好了。等你把同一份代码搬到单核真 MCU 上跑,这个 bug **反而消失了**——或者反过来,你在单核 MCU 上怎么都复现不了某个竞态,搬到 host 多核 PC 上却频频出现。

**为什么**会这样,要理解单核抢占式调度和多核真并发的本质差别。单核 MCU(哪怕跑 RTOS)在**任一时刻只有一个任务真在跑**,任务之间的「并发」是**抢占式时间片轮转**造出来的假象——两个任务不会同时在执行,它们对共享变量的访问在时间上是错开的,只要每段访问是「不可被打断的临界区」(比如进了 `taskENTER_CRITICAL`),就不会有真并发踩踏。所以单核上,一个临界区只要做到「关抢占/关中断」就安全了。但多核 PC 上,你的多个 FreeRTOS 任务被 POSIX port 映射成多个 pthread,宿主 OS **真的会把它们同时调度到不同 CPU 核上跑**——这下就是真并发了。两个任务可能同时(物理上的同一时刻)读写同一个共享变量,「关抢占」对另一个核上的任务毫无约束力。于是那些在单核上「因为时间错开而侥幸不出事」的临界区(忘了加锁的读改写、用了非原子操作),在多核 host 上被**赤裸裸地暴露**成真竞态。

**对策**分两层。**第一层是认清这条差异的「方向」**:host 多核上暴露的竞态,大多是「真 bug」——只是它在单核 MCU 上因为时间错开而侥幸没发作,不代表代码对。所以 host 上偶发的崩/错乱,**先别怪 host**,认真查有没有忘了保护的共享访问。**第二层是用正确的同步原语保护临界区**:凡是多任务共享的可变状态(计数器、缓冲区、链表),要么用互斥量([08 资源管理](../tutorial/08_resources/))包成临界区、要么用队列([05 队列](../tutorial/05_queues/))做无锁的按值传递(队列的 send/receive 内部是原子的,不用你再加锁)。特别要注意 FreeRTOS 的 `taskENTER_CRITICAL`/`taskEXIT_CRITICAL` 在 host port 上的语义——它关的是「抢占」、不一定关「多核真并发」,所以 host 上**别拿 `taskENTER_CRITICAL` 当万能锁**,跨核共享的还是老老实实用 mutex 或队列。另外,排查 host 上的偶发竞态有个利器:[12 调试章](../tutorial/12_debugging/)的运行时统计(`configGENERATE_RUN_TIME_STATS`)能告诉你各任务 CPU 占用,配合周期性的状态快照(`uxTaskGetSystemState`)能看到「谁在什么时候在跑」,对定位「两个任务是否真并发踩到同一资源」很有帮助。

**真硬件上怎样**:如果是单核 MCU,这条「多核竞态」不存在——单核上时间错开,关抢占就够了,所以你那些「在 host 上偶发、MCU 上不复现」的 bug,移到 MCU 上可能确实消停了(但代码本身还是错的,换个 RTOS 或上双核 MCU 就会复发,别留隐患)。如果是**多核 MCU**(比如双核 ESP32、RP2040 的两个核),那 host 多核暴露的竞态在多核 MCU 上同样会发作——这时 host 反而是个不错的「竞态放大器」,帮你在上板前就把真并发的 bug 暴露出来。所以这条坑的真正教训是:**host 多核是个竞态检测利器,它暴露的几乎都是真问题;别因为「MCU 上不复现」就忽略它**。

## 小结

这一类坑的共性是「host 和真 MCU 在时序/并发模型上根本不同」:host 不实时(timing 不可信)、host 用信号切换(野线程直调 FromISR 会 hang、阻塞 syscall 会冻死系统)、host 多核(暴露单核隐藏的竞态)、host 没有真中断(得手动注入事件源)。它们在真硬件上要么消失、要么反向——所以 host 测试结果的**逻辑**可信、**时序和并发边界**要打折看。下一篇 [资源与回收](./03-resources-and-recovery.md) 我们收最后三类坑:栈溢出检测失效、vTaskDelete 的资源回收差异、忙等饿死和 CPU 占满。

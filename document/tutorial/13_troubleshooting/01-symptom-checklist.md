# 常见问题速查:现象 → 原因 → 对策

这一页把[章节总览](./index.md)那张速查表逐条展开。每一条都按固定的三段式来读:**现象**(你在控制台/调试器里看到什么)→**原因**(底层机制为什么会这样)→**对策**(怎么改、怎么预防)。读这一页最好把它当工具书用——真踩到某个坑时,按「现象」那一列对号入座,跳到对应小节看机制和改法。

## malloc failed:堆被吃光

**现象**是最直白的:你在开发期把 `configUSE_MALLOC_FAILED_HOOK` 开着(本教程模板就是 1),一旦 `pvPortMalloc` 在 heap_4 里分配失败,它就会调 `vApplicationMallocFailedHook`,而我们 `app_hooks.c` 里那个 hook 直接转去 `vAssertCalled`——于是你看到一行 `ASSERT FAILED: <文件>:<行号>`,程序停在一个 `while` 死循环里不动了。另一类相关现象是 `xTaskCreate` 静默返回 `pdFAIL`(其实是 `errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY`),新建的任务根本没被造出来、自然也不跑——这种不会触发 assert,更隐蔽,所以**每次 `xTaskCreate` 都要检查返回值**。

**原因**只有一条:堆不够了。但「为什么不够」有好几个常见的子原因。最经典的是**任务栈太大**:POSIX port 下每个任务栈被强制到 `PTHREAD_STACK_MIN`(16384 字 × 8B = 128KB),你建十几个任务光栈就要 1MB+,很容易把堆吃光——这是 host 模拟独有的体量错觉([03 内存章](../03_memory/)讲过),真 MCU 上栈才几百到几千字。其次是**对象泄漏**:队列、信号量、事件组只 `xQueueCreate` 不 `vQueueDelete`,或者任务只 `xTaskCreate` 不 `vTaskDelete`,它们占的堆永远不还。再次是**碎片**:频繁分配释放大小不一的块,把堆切成一堆小碎片,虽然 `xPortGetFreeHeapSize` 看着还有不少,但凑不出一个连续的大块——heap_4 会合并相邻空闲块、缓解碎片,但治不了跨活跃块的洞。

**对策**分三层。**第一层是提前看见**:用 `xPortGetMinimumEverFreeHeapSize()` 读「自启动以来堆掉到的最低点」——这是个高水位线,它贴近 0 就说明「再分配一次就要 malloc failed 了」,你完全可以在它真炸之前就加日志、抬堆。这是为什么前面坚持用 heap_4 而不是 heap_3(heap_3 不提供这俩函数)。**第二层是抬堆/控对象**:`configTOTAL_HEAP_SIZE` 给够(本教程 demo 都抬到 2MB),审查有没有只建不删的泄漏。**第三层是查返回值**:每个 `xTaskCreate`/`pvPortMalloc` 都判返回值,失败时打日志而不是让程序带着半残状态继续跑。这三个对策合起来,基本能把 malloc failed 消灭在发生前。

## 栈溢出:host 下是「盲区」

**现象**在真硬件上很明确:`configCHECK_FOR_STACK_OVERFLOW` 开着的话,任务切换时内核发现栈被踩(涂的魔数被覆盖),调 `vApplicationStackOverflowHook`,程序停下、告诉你哪个任务爆栈了。但**在 host 模拟下,这个现象你根本看不到**——hook 永远不触发,程序也不会因为爆栈而停下(除非你递归到把 pthread 自己的栈也撑爆,那是另一回事,通常是 segfault)。

**原因**在 POSIX port 的实现里:内核的栈溢出检测靠「给任务栈涂魔数、切换时检查有没有被踩」,但 POSIX port 把每个任务映射成一个 pthread,任务**真正的调用帧压在 pthread 自己的栈上**(由宿主 glibc 管),FreeRTOS 给任务准备的那块 `pxStack` 缓冲区主要用来存 `Thread_t` 元数据 + 当大小提示,**并不承接实际调用帧**。内核够不着 pthread 的栈去涂魔数,检测自然失效。更扎心的是,连 `uxTaskGetStackHighWaterMark` 水位线探针也不可靠——它扫的是 `pxStack` 缓冲区里涂的魔数,但真实调用帧不在那儿,所以这个数几乎不随你的递归深度变化。

**对策**要分场景。**host 模拟下**:认清这是盲区,别指望自动检测;靠**代码审查**估算每个任务的栈需求(深递归?大局部数组?嵌套调用深吗?),给足 `usStackDepth`,外加 review。**真硬件上**:把 `configCHECK_FOR_STACK_OVERFLOW` 设成 2(方法二最严,既检查栈指针越界也检查魔数),开发期始终开着;同时 `uxTaskGetStackHighWaterMark` 在真硬件上是可信的,定期打印各任务的水位,把 `usStackDepth` 收紧到略大于峰值、省 RAM。这条坑在[仿真坑点](../../pitfalls/)的「栈双重性」条目里有专门记录,移到真板子前务必留意。

## 优先级反转 + starvation:高优任务被中优拖死

**现象**很坑爹:你明明给某个任务设了高优先级,它却莫名其妙地迟迟不响应,延迟大到几百毫秒甚至秒级——而系统里根本没有比它更高优先级的任务在跑。**starvation** 是它的近亲:某个低优先级任务长期得不到运行机会,像是被「遗忘」了。

**原因**是经典的三任务优先级反转(priority inversion)。场景是这样:低优先级任务 `Low` 持有一把(二值)信号量正在干长活;这时高优先级任务 `High` 要这把信号量,撞上、被阻塞;恰好来个中优先级任务 `Mid`(优先级介于两者之间),它一就绪就把 `Low` 抢走了——`Low` 没法继续干、还不掉信号量,`High` 就被 `Mid` 活活拖住。诡异之处在于:`Mid` 的优先级明明**低于** `High`,本不该影响 `High`,却因为 `Low` 夹在中间持锁,把 `High` 的延迟「传染」给了 `Mid`。这就是「反转」——优先级在效果上被倒挂了。starvation 同源:`Mid` 忙等不让出,不光拖 `High`,也把 `Low` 饿死(`Low` 还没机会还锁),`High` 就更没指望了。

**对策**有两条,看场景选。**最对症的是把二值信号量换成 mutex**:`xSemaphoreCreateMutex()` 建出来的互斥量带**优先级继承**(priority inheritance)——`Low` 持锁时被 `High` 撞上,`Low` 会被临时抬到 `High` 的优先级,`Mid` 就抢不动它了,`Low` 赶紧干完还锁,`High` 早拿锁。优先级继承把「反转」这个洞直接堵上了,这正是「保护共享资源该用 mutex 而不是二值信号量」的根本原因([08 资源管理章](../08_resources/)讲透了这个差别)。**另一条对策是缩短/避免持锁期间的忙等**:别在持锁时干长活、尤其别在持锁时忙循环;`Mid` 那种忙等任务里也要加 `taskYIELD`/`vTaskDelay` 让出,避免它把低优任务饿死。如果场景不允许换 mutex(比如 ISR↔任务同步,mutex 不能在 ISR 用),那就靠缩短临界区 + 让出 CPU 来缓解。

## 队列满丢消息:非阻塞 send 的语义后果

**现象**:你用队列在生产者和消费者之间传数据,跑一段时间后发现「数据少了几个帧」「某些采样没了」。翻日志又没报错——程序运行得好好的,只是数据悄悄地少了。

**原因**几乎总是**非阻塞 `xQueueSend` 撞上满队列**。生产者用 `xQueueSend(q, &item, 0)`(第三个参数 `0` = 零超时 = 不等待),队列一旦满了,这个调用立刻返回 `errQUEUE_FULL`,这一帧就被丢弃——而且不报错、不停下,所以你根本不会在日志里看到「丢了」。这在「生产快、消费慢」的组合下几乎必然发生:生产者每个循环都发,消费者处理一帧要 80ms,队列容量才 2 格,几毫秒就填满,之后生产者的发送全是无效投递。这不是 bug,是「零超时 send + 满队列」的**语义后果**——你明确说了「队列满就别等、立刻返回」,那满了它当然就立刻返回(失败)。

**对策**有三条,按你的语义需求选。**(a) 最新值语义**:`xQueueOverwrite`(只允许用在容量为 1 的队列上),满了就**覆盖最旧的一帧**,保证「消费者永远读到最新值」——适合传感器采样这种「我只在乎最新读数、旧的丢了无所谓」的场景,dashboard 脊柱就是用这招。**(b) 阻塞反压**:生产者用 `xQueueSend(q, &item, 超时)` 带一个阻塞超时,队列满了就等(等到消费者腾出位置),这会把「快」的生产者反压到消费者的速度——适合「一帧都不能丢」的场景,代价是生产者可能被阻塞。**(c) 配额限速**:用一个计数信号量做「生产配额」,生产者每发一帧 take 一个 token、消费者每消费一帧 give 回一个,把生产速率硬性钳在消费速率之下。三条里第一条最省事、第二条最通用、第三条最严格,看你丢帧能不能容忍来选。

## 死锁:锁顺序相反构成环形等待

**现象**:两个(或更多)任务突然永久卡住,谁也不跑了,像是「集体罢工」。你 attach 上去看,它们都 blocked 在某个 `xSemaphoreTake` 上,等一把对方持有的锁。

**原因**是经典的**环形等待(circular wait)**。两个任务各先拿一把 mutex,再去抢对方的另一把,而且**两人拿锁的顺序相反**:任务 A 先拿锁 1 再拿锁 2,任务 B 先拿锁 2 再拿锁 1。于是 A 拿着锁 1 等锁 2、B 拿着锁 2 等锁 1——谁也不撒手,谁也拿不到第二把,两个任务永久 blocked。只要「多个任务以不同顺序获取同一组锁」这个条件成立,死锁就可能发生,而且往往是偶发的(平时正好错开没事,某次时序凑巧就卡死),debug 极其折磨。

**对策**首推**全局统一的锁获取顺序**:约定整个代码库里「要同时拿锁 1 和锁 2,永远先 1 后 2」,环形等待就构不成——这是从根上消除死锁的标准做法。其次是**持锁时带超时**:`xSemaphoreTake` 传一个超时而不是 `portMAX_DELAY`,到点拿不到就放弃、回退、重试或报错——这不能预防死锁,但能在 debug 时**探测**到死锁(到点拿不到 = 卡在环形等待里了),本章 demo 就是这么「探测」而不是真挂的。再次是**缩短临界区、别在锁里等另一把锁**:临界区越短、嵌套越浅,死锁窗口越小。组合起来:设计期统一锁顺序治本,运行期带超时探测兜底,基本能把死锁治住。

## assert 触发:开发期的「快速失败」是好事

**现象**:`ASSERT FAILED: <文件名>:<行号>` 然后程序停住。新手第一反应往往是「糟了,出 bug 了」,但其实这是**好事**——它意味着你在开发期就发现了一个用法错误,而不是让它潜伏成生产环境里一个幽灵 bug。

**原因**是 `configASSERT`(开发期建议始终开)拦下了各种 API 误用:传了 NULL 句柄、给任务设了越界优先级(≥`configMAX_PRIORITIES`)、在 ISR 里调了任务版 API、在不允许的上下文里调阻塞函数……内核在这些入口处都埋了 `configASSERT`,一发现条件不满足就调 `vAssertCalled` 停下、把出错的文件名+行号甩给你。所以看到 assert,定位极其直接:文件名+行号指到内核源码的检查点,你顺着调用栈往上找一层就是你的误用代码。

**对策**只有一条:**开发期永远开着 `configASSERT`,出了 assert 别绕过、去读行号**。本教程的 `app_hooks.c` 里 `vAssertCalled` 会打印 `ASSERT FAILED: ...` 然后进一个 `while` 循环停下(调试器里把那个变量改非 0 可继续),这正是「快速失败」的标准实现。[12 调试章](../12_debugging/)专门演过一次故意触发 assert 的现场,值得对照。注意一点:发布版有时会为了省代码体积/性能关掉 assert,但**内核机制相关的项目不建议关**——一个静默的 NULL 句柄 bug 比 assert 停下可怕得多。

## 任务不跑(idle 抢占 / starvation / 优先级设错)

**现象**:你新建了一个任务,`xTaskCreate` 返回 `pdPASS`(创建成功),但它就是不跑,`console_print` 一行没打出来,像是没被调度过。

**原因**通常有三类。**最常见的是 starvation**:系统里有个高优先级任务在忙等、不让出 CPU(`vTaskDelay`/阻塞 API 都不调),它把所有低优先级任务全饿死了,你新建的那个自然也排不上。**其次是优先级设错**:你把新任务优先级设成了 0(等于 `tskIDLE_PRIORITY`),它和内核 idle 任务挤同一档,行为不可预期,经常被 idle 抢走;FreeRTOS 规定 `tskIDLE_PRIORITY` 是 idle 专属,应用任务至少给 `+1`。**再次是阻塞条件永远不满足**:任务一启动就 `xQueueReceive`/`xSemaphoreTake` 在某个永远没人 give/send 的对象上死等,自然永远不往下走。

**对策**对症下药。先查有没有忙等的高优任务——这类任务里必须加 `vTaskDelay` 或阻塞式 API 让出 CPU([04 任务章](../04_tasks/)讲过,善用 blocked 是多任务并存的前提)。再查新任务的优先级是不是 ≥ `tskIDLE_PRIORITY + 1`。最后查它阻塞等的对象有没有人真去 give/send——用 `uxTaskGetSystemState` 拍一张状态快照([12 调试章](../12_debugging/)演过),看它是不是长期 `Blocked`,一目了然。这一类问题几乎都能靠「状态快照 + 审查优先级/阻塞源」定位,不需要玄学。

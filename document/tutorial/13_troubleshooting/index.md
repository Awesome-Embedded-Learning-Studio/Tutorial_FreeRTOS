# 排错

## 这章解决什么问题

前面十二章我们一路把 FreeRTOS 的核心原语——任务、队列、软件定时器、中断、互斥量、事件组、任务通知、内存、调试——一个个拆开讲透,每一章都配了能 build 能跑的 demo。但真实工程里,你不会是「单独用一个原语、它乖乖按预期工作」这么顺。你会撞上一堆横跨多条原语、形态各异的「症状」:程序跑着跑着就停在某个 assert 上不动了、某个高优先级任务莫名其妙地迟迟不响应、队列里数据少了几个、两个任务互相等谁也不撒手、新加的任务死活不跑……这些症状的共同点是:**它们大多不是某个 API 用法的语法错,而是「机制理解错」或「资源/时序设计错」**。这一章就是把这些散落在前面各章的坑,系统化地收一遍,给你一张「看到现象就能对上原因、对上原因就知道怎么改」的速查表。

排错和前面每一章都不太一样,它**不属于某一条原语**,它是横向能力。所以这一章的 demo 也不是一个常驻多任务应用,而是一个「故障博物馆」:一个 Driver 任务顺序跑五个互相隔离的小场景,每个复现一类经典故障,在输出里打印「现象 → 原因 → 对策」,跑完一个清掉再进下一个。这样所有故障能在一次 build/run 里走完,而且彼此不串味——不会因为 A 场景挂了拖死 B 场景。这套组织方式本身也值得学:调试时把可疑现象隔离成最小复现,比在一个大系统里乱翻高效得多。

## TL;DR:常见问题速查表

下面这张表是本章的索引,每一条都对应一个「现象 → 原因 → 对策」三段式。新手最常踩的几条加粗,排在前面。详细的诊断思路和复现 demo 在后面的子页里展开。

| 现象 | 最可能的原因 | 核心对策 |
|------|------------|---------|
| **`vApplicationMallocFailedHook` 触发 / `ASSERT FAILED`** | 堆不够(任务栈、对象、临时分配吃光) | 抬大 `configTOTAL_HEAP_SIZE`;用 `xPortGetMinimumEverFreeHeapSize` 提前监控水位;查有没有任务泄漏(只建不删) |
| **高优先级任务迟迟不响应(几百 ms 级延迟)** | **优先级反转**(低优持锁、中优抢占、高优被拖) | 把二值信号量换成 **mutex**(带优先级继承);或缩短临界区、不在持锁时忙等 |
| 某个低优先级任务长期不跑(starvation) | 一个高优先级任务忙等不让出 CPU | 高优任务里加 `vTaskDelay`/阻塞式 API/`taskYIELD`;善用 blocked 让出 |
| **队列里消息丢了 / 数据少了几帧** | 生产快、消费慢、队列满,非阻塞 `xQueueSend` 返回 `errQUEUE_FULL` | `xQueueOverwrite`(最新值语义)、带阻塞超时反压、或计数信号量做配额 |
| **两个(或多个)任务永久卡住不跑** | **死锁**(锁顺序相反构成环形等待) | 全局统一的锁获取顺序;持锁时带超时;尽量缩短临界区、别在锁里等另一把锁 |
| **`ASSERT FAILED: tasks.c:...` 程序停住** | API 用法错(NULL 句柄、越界优先级、ISR 里调错 API 版) | 看 assert 的文件名+行号定位;开发期始终开 `configASSERT` |
| 新建的任务死活不跑 | 优先级设错(=0 和 idle 同档被抢)、或更高优先级任务忙等把它饿死 | 优先级给 `tskIDLE_PRIORITY + 1` 以上;确保有高优任务让出 |
| `xTaskCreate` 返回 `pdFAIL` | 堆不够分配 TCB/栈(`errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY`) | 查堆余量;栈别给太大;减少常驻任务数 |
| **栈溢出但 host 下毫无反应** | POSIX port 下 `configCHECK_FOR_STACK_OVERFLOW` 不触发,水位线也不可靠 | host 是「盲区」;真硬件上 `configCHECK_FOR_STACK_OVERFLOW=2`;设计期就给足栈、用代码审查估深度 |

## 这章的边界:host 模拟下哪些坑「演不全」

排错章有个特别要诚实交代的点:**有几类故障在 host 模拟下没法「真演」**,因为演了 demo 就挂了、后面就没法继续。最典型的是真 `malloc failed`(它会进 `vApplicationMallocFailedHook` → `vAssertCalled` 死循环,demo 当场停住)和真死锁(任务永久 blocked,demo 卡死、Ctrl-c 才能退)。所以本章 demo 的处理是:**用「超时探测 + 打印诊断」来复现「卡住的现象」,而不是真挂在那儿**。这样五个故障能在一次 build/run 里全走完,任何一个都不会把 demo 拖死。这个取舍本身就值得记住——真硬件调试时你照样会看到真挂,但那时你已经照着这张速查表对过症状了。

另一类 host 演不全的是**栈溢出检测**:`configCHECK_FOR_STACK_OVERFLOW` 在 POSIX port 下压根不触发(内核够不着 pthread 的栈去涂魔数),连 `uxTaskGetStackHighWaterMark` 水位线探针都几乎不动(任务真正的调用帧压在 pthread 自己的栈上,不在内核管的那块 pxStack 里)。所以 host 下栈溢出基本是「盲区」,我们只能诚实指出这点、把可靠诊断留给真硬件。这两条边界在[仿真坑点](../../pitfalls/)里有更细的记录,排错前扫一眼建立预期。

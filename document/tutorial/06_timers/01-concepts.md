# 软件定时器:概念与机制

回到[章节总览](./index.md),这一页把软件定时器的概念和机制讲透;下一页配一个能跑的独立 demo 把这些演给你看,再下一页嫁接到 dashboard 脊柱上。

## 这章解决什么问题

前面几章里,凡是要「每隔一段时间做一件事」,我们的写法千篇一律:在任务里写一个 `for( ;; )`,干完活 `vTaskDelay(pdMS_TO_TICKS(N))` 睡 N 毫秒,醒了再干。dashboard 的 sensor 采集任务、内存监控任务、04 章的三个 Worker,全都是这个套路。这套写法能跑,但有个问题:节奏是谁定的?是「这个任务自己」。每个任务各自抱着一个 `vTaskDelay`,节奏散落在各任务内部,你想统一调度它们、想让某个任务「被别人叫醒再干活」而不是「自己定闹钟」,这套写法就力不从心了。

软件定时器就是 FreeRTOS 给的另一套思路:把「每隔一段时间触发一次」这件事从任务里抽出来,变成一个独立的、由内核管理的对象——定时器。你创建它、启动它,到点内核就帮你调一个回调函数;至于回调里干什么、干完之后谁接着跑,那是你的事。这一章我们要做的,就是动手建一个周期定时器和一个单次定时器,把它们到期触发的时刻一行行打出来,把「周期」和「单次」的差别、以及一个新手最容易栽的坑——回调到底跑在谁的上下文里、为什么不能在里面阻塞——一起看清楚。

## xTimerCreate:一个定时器是怎么造出来的

创建软件定时器用一个 API,签名长这样:

```c
TimerHandle_t xTimerCreate( const char * const pcTimerName,
                            const TickType_t xTimerPeriodInTicks,
                            const UBaseType_t uxAutoReload,
                            void * const pvTimerID,
                            TimerCallbackFunction_t pxCallbackFunction );
```

我们逐个参数拆。第一个 `pcTimerName` 是给定时器起的名字,和任务名一样主要给调试用——`vTaskList`、`uxTaskGetSystemState` 里都会显示它,内核会把它拷一份进定时器结构体(长度上限同样是 `configMAX_TASK_NAME_LEN`,模板里 12)。给它起个一眼能认出来的名字(`"Periodic"`、`"SampleTmr"`)比 `t1`/`t2` 有用得多。

第二个 `xTimerPeriodInTicks` 是周期,单位是 tick——注意不是毫秒,所以我们到处用 `pdMS_TO_TICKS()` 把毫秒换算成 tick。这一位在不同类型的定时器里含义略有不同:周期定时器它表示「两次触发之间的间隔」,单次定时器它表示「从启动到第一次(也是唯一一次)触发的延迟」。tick 频率是 `configTICK_RATE_HZ`(模板里 1000Hz),所以 host 模拟下 1 tick = 1ms,换算系数恰好 1:1;真硬件上 tick 频率常是 100Hz,换算系数会变,这也是为什么我们坚持写 `pdMS_TO_TICKS(500)` 而不是裸写 `500`。

第三个 `uxAutoReload` 是本章的核心开关,它一位决定了这个定时器是周期还是单次:`pdTRUE` 是周期定时器(auto-reload,到期后自动重装、周而复始),`pdFALSE` 是单次定时器(one-shot,到期一次就停、打完一枪就退休)。这两种模式的差别,后面 demo 会直接演给你看。

第四个 `pvTimerID` 是回调里能拿到的「身份标识」。当你多个定时器共用同一个回调函数时(完全允许,也常见),回调被调用时怎么知道「现在是我哪个定时器响了」?就靠这个 ID——内核把它原样作为回调参数传进来。本章 demo 两个定时器各用各的回调,不需要靠 ID 区分,这里传 `NULL` 即可。第五个 `pxCallbackFunction` 是回调函数指针,签名必须是 `void fn( TimerHandle_t )`,那个参数就是触发它的定时器自己的句柄。返回值是 `TimerHandle_t`,创建失败(heap 不够)返回 `NULL`,致命错误直接 `configASSERT` 兜住。

## 单次 vs 周期:就差一位 uxAutoReload

单次和周期的全部区别,就在 `uxAutoReload` 这一位上,但它们的行为差别很值得记牢。周期定时器(`pdTRUE`)一旦启动,就会按你给的周期**周而复始地触发**:到期、调回调、自动重装下一个周期、再到期、再调回调……只要你不 `xTimerStop` 它或删掉它,它就一直响下去,响的间隔恒定。单次定时器(`pdFALSE`)则是**启动后只响一次**:从你 `xTimerStart` 那一刻起,等一个周期的时间,响一次回调,然后就再也不响了——它进入了「已触发、dormant」状态,除非你再次 `xTimerStart` 重新启动它,它才会再响下一次。

这两种模式对应完全不同的用法。周期定时器适合「需要持续、固定节奏地做一件事」的场景——dashboard 里驱动 sensor 周期采样、心跳闪灯、周期性喂看门狗,都是它的地盘。单次定时器适合「过一段时间做一次、做完拉倒」的场景——上电后延迟 2 秒再启动某个模块、按键去抖(按下后等 30ms 再判定,只判一次)、超时重传(发出去一个包后挂一个 N 秒的单次定时器,收到了就停,没收到就触发重传回调)。把「周期」和「单次」这对概念和现实里的需求对上号,你拿到一个定时需求就能立刻判断该用哪种。

## 回调跑在 timer 服务任务上下文:这条铁律记死

到这里概念都不难,真正的坑在下一个知识点上,也是新手栽得最狠的地方:**定时器回调不是普通任务函数,它跑在「定时器服务任务」(timer service task,daemon task)的上下文里**。这个任务是内核在你开了 `configUSE_TIMERS` 之后自动建的——你在 04 章那张任务快照里见过它,名字叫 `Tmr Svc`,优先级被模板设成 `configMAX_PRIORITIES - 1`(最高档)。所有定时器的回调——不管你建了多少个定时器、不管它们周期差多少——全部串行地挤在这同一个服务任务里依次执行。

这带来一个直接后果,也是本章最该带走的认知:**一个回调没返回,后面的定时器就只能排队干等**。服务任务只有一个,它在执行回调 A 的时候,回调 B 的定时器就算已经到期了,也得等 A 返回才能轮到 B。所以你在回调里能干什么、不能干什么,有一组很硬的规矩。回调里**绝不能阻塞**——不能 `vTaskDelay`、不能在空队列上死等、不能拿互斥量长时间霸占;回调里也**不能干长活**——什么「在回调里跑一段几百毫秒的计算」是绝对不行的。

回调的正确姿势是「立刻做完一件极短的事,然后立刻返回」,典型的极短事是:往队列里投一帧、给某个任务发一个通知、置一个事件位、更新一个共享变量。把真正的耗时工作丢给普通任务去做——回调只负责「通知一声」,干活的交给被通知的任务。这件事不是建议,是铁律:一旦你在回调里 `vTaskDelay(500)` 假装在干活,你卡住的不只是这一个定时器,而是整个服务任务,所有别的定时器全部集体迟到——你的周期定时器会变得不再周期,单次定时器的「2 秒后触发」可能拖成 2.5 秒。这种 bug 极其隐蔽,因为它不会崩、不会断言,只是「定时器不准了」,排查起来很折磨人。

## 定时器命令队列:为什么 xTimerStart 不立刻生效

理解了回调的上下文,顺带就能理解另一件事:**你调 `xTimerStart`(以及 `xTimerStop`、`xTimerChangePeriod` 这些 API)时,定时器并不是立刻就被启动的**。整个软件定时器子系统是靠一条「定时器命令队列」(timer command queue)串起来的,工作流程是这样:你调 `xTimerStart`,这个函数并不直接去碰定时器链表,而是往命令队列里塞一条命令(「请帮我启动这个定时器」),然后(如果服务任务正阻塞在这条队列上)把它唤醒;真正把定时器挂上链表、开始计时,是服务任务从队列里取出这条命令之后才做的事;到期时,服务任务再调你的回调。

这个设计有两层含义。第一,**定时器的精度受限于「服务任务被调度的及时性」和「命令队列的长度」**。命令队列满了(模板里 `configTIMER_QUEUE_LENGTH=20`),你投的命令就会失败或被推迟;服务任务优先级不够高、被高优先级任务压着,定时器回调就会迟到。所以模板故意把服务任务优先级设到最高档(`configMAX_PRIORITIES - 1`),就是为了尽量让它被及时调度。第二,**软件定时器不是硬件中断**,host 模拟下更谈不上实时——它的「准时」是相对于调度器和服务任务的,不是相对于绝对墙钟的。教学边界章里讲过,实时性、中断延迟这些在 host 模拟下根本保证不了,软件定时器也不例外,别拿它当硬实时的兜底。

## 几个配置旋钮:configUSE_TIMERS 一家子

软件定时器能不能用,由 `FreeRTOSConfig.h` 里一组开关控制,我们逐个过一遍。最上位的是 `configUSE_TIMERS`:设成 1 才会编入 `timers.c`、内核才会自动建那个服务任务;设成 0 整个定时器子系统被裁掉,你调任何 `xTimer*` API 都链接不到。模板里是 1,本章 demo 直接用。

`configTIMER_TASK_PRIORITY` 是服务任务的优先级。前面说了,模板故意把它设到 `configMAX_PRIORITIES - 1`(最高档),理由就是「让定时器回调尽量被及时调度、少迟到」。你可以往下调(比如调到中等优先级),但代价是回调可能更晚才轮到——一般来说这个值默认就别动,保持最高档是对的。

`configTIMER_TASK_STACK_DEPTH` 是服务任务的栈深,模板里设成 `configMINIMAL_STACK_SIZE * 2`——也就是两倍最小栈。为什么是这个值?因为**所有定时器回调的局部变量、调用栈帧,全压在这一个服务任务的栈上**。你建的定时器越多、回调里用的局部变量越大,这栈就要越深。如果你某个回调里定义了一个大数组、或调用了一个调用层次很深的函数,就可能把服务任务的栈撑爆——而这个栈爆了是「全员定时器」一起死,不是只死一个。所以把服务任务栈设成两倍最小栈是给回调留余量;真到回调很重的场景,这个值得继续往上抬。

最后还有 `configTIMER_QUEUE_LENGTH`(命令队列长度,模板 20)和 `INCLUDE_xTimerGetTimerDaemonTaskHandle` 等开关,前者决定能积压多少条未处理的命令,后者决定能不能拿到服务任务的句柄。这几个一般不用动,知道有它们就行。

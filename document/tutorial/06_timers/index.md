# 软件定时器

## 这章解决什么问题

前面几章里凡是要「每隔一段时间做一件事」,我们的写法千篇一律:任务里一个 `for( ;; )`、干完活 `vTaskDelay` 睡 N 毫秒、醒了再干——dashboard 的 sensor 任务、内存监控任务、04 章的三个 Worker,全都是这个套路。这套写法能跑,但节奏散落在各任务内部、无法被统一调度。软件定时器是 FreeRTOS 给的另一套思路:把「每隔一段时间触发一次」这件事从任务里抽出来,变成内核管理的独立对象——你创建它、启动它,到点内核就帮你调一个回调。这一章我们把软件定时器的全貌(五个参数、单次/周期、回调上下文、命令队列、配置旋钮)讲透,配上一个能跑的独立 demo,再嫁接到 dashboard 脊柱用周期定时器驱动 sensor 采样。

## TL;DR:关键结论

- **`xTimerCreate` 五个参数**:名字(调试用)、周期(tick,周期定时器是间隔、单次定时器是首次延迟)、`uxAutoReload`(pdTRUE 周期 / pdFALSE 单次,两种模式的全部区别)、pvTimerID(多定时器共用回调时区分身份)、回调函数。
- **单次 vs 周期**:就差 `uxAutoReload` 一位——周期周而复始、单次响一次就 dormant,分别对应「持续节奏」和「过段时间做一次」两类需求。
- **回调跑在 timer 服务任务上下文**:所有回调串行挤在这一个任务里,所以回调必须极短、绝不阻塞(`vTaskDelay`/死等/长活全禁止),正确姿势是「回调只通知、任务才干活」,否则拖垮全体定时器。
- **定时器命令队列**:`xTimerStart` 这类 API 不立刻生效——它投命令、服务任务取命令才真正执行,所以软件定时器精度受服务任务调度及时性和队列长度限制,不是硬件中断、host 模拟下不实时。
- **配置旋钮**:`configUSE_TIMERS` 是总开关,`configTIMER_TASK_PRIORITY` 默认最高档(让回调少迟到),`configTIMER_TASK_STACK_DEPTH` 给回调留栈(所有回调共用这一个栈,回调重了得往上抬)。

## 关于踩坑

软件定时器最该记的坑——回调里阻塞会拖垮全体定时器、host 模拟下精度受调度抖动影响(不是硬实时)——散落在 [概念与机制](./01-concepts.md) 的「回调上下文」和「命令队列」两节。至于「软件定时器和真 MCU 在行为上的系统差异」,收在 [仿真坑点](../../pitfalls/),建议对照本章读一遍。下一章 [中断管理](../07_interrupts/) 进入 host 模拟最棘手的一块:ISR 上下文、`*FromISR` API、用信号量做中断和任务的同步——到时候你会发现,软件定时器回调(以及 tick hook)正是 host 模拟下「相对安全地模拟中断源」的常用落脚点,本章讲的「回调上下文」会直接派上用场。

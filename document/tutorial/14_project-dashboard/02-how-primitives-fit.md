# 原语如何协作:串起 03~13

如果你从头读到这儿,这一页读起来会非常爽——前面每一章埋的伏笔,在这里全部兑现。我们不再重复讲每个原语的机制(那在各章正文里讲透了),只讲它**在 dashboard 这个工程里扮演什么角色、为什么是它而不是别的**。这正是集成章的意义:不是学新东西,是看老的怎么合体。

## [03] 堆内存管理:HeapMon 任务和两个 Phase 1 配置

dashboard 能跑起来的第一道地基是堆。`configTOTAL_HEAP_SIZE` 被抬到了 **2MB**,堆实现选的是 **heap_4**(不是 02 环境章那套默认的 heap_3)。这两个配置是 Phase 1 实测出的硬前提,缺一不可:heap_3 不实现 `xPortGetFreeHeapSize` / `xPortGetMinimumEverFreeHeapSize`,而 HeapMon 任务就指着这俩函数读数;另外 POSIX port 每个任务栈都有 16KB+(`PTHREAD_STACK_MIN`),固定大小的静态 heap 数组若用默认值,连几个任务都装不下、直接触发 `malloc failed hook`。这两个选择在[堆内存管理](../03_memory/)那章解释过,这里它是地基。

HeapMon 任务本身极简:每 2 秒探一次堆、打印 `free` 和 `min_ever`,优先级压最低。它存在的意义就是让你在运行时**实时监控堆水位**——`min_ever` 这个"历史最低水位线"尤其有用,它告诉你"曾几何时堆差点被吃光",是设计期估堆大小、运行期抓泄漏的利器。这套"周期性探堆 + 打印水位"的模式,就是 03 章那篇 dashboard 增量的直接产物。

## [04] 任务管理:sensor/display 的切分与优先级

dashboard 的骨架是 04 章拆出来的——把原本单一的心跳任务一分为二:**Sensor(采集)** 和 **Display(显示)**,各管一摊、优先级不同。这个切分不是为拆而拆,而是真实工程里"采集"和"显示"本来就是两件时序敏感度完全不同的事:采集在乎"到点就采、别被拖延",显示在乎"刷新别太快也别太慢、给人看"。把它们拆成两个任务、给 Sensor 更高的优先级,正是为了让"采集时序敏感"这件事被调度器尊重——周期滴答一到,Sensor 就该被立刻切上来,哪怕 Display 正在打印中途。

这一页后面会反复看到,Sensor 优先级 `+3`、Display `+2` 这个分层,是后面所有协作能正常工作的前提。状态机层面它俩也呼应 04 章:Sensor 大部分时间 blocked 在信号量上、Display blocked 在事件组/队列上,只在被唤醒时短暂 running——这正是 04 章那张 ready/running/blocked 状态机在真实代码里的活体。

## [05] 队列管理:容量 1 的"最新值寄存器"

队列是整条数据主链路的管道。Sensor 采到帧 `xQueueOverwrite` 投进去,Display 阻塞 `xQueueReceive` 取出来。两个刻意的设计都来自 05 章:一是**按值拷贝**(队列把整帧 `SampleFrame_t` 拷一份过去,读方永远拿到一帧完整快照,没有撕裂);二是**容量 1 + `xQueueOverwrite`**(新采样覆盖旧的,"最新值"语义,不积压)。这里没有用"容量 N + 带阻塞超时反压"那套"一帧不丢"语义,因为仪表盘的读者是人、只在乎当前值——两种相反语义怎么选,05 章对比过,这里采的是适合仪表盘的那种。

队列在这里替代了 04 章骨架最初用的那根"裸全局变量"。为什么非换不可?因为裸全局变量把"传数据"和"同步"拆成了两件事、还留了竞态窗口;队列一把把这两件事一次做完,按值拷贝保证不撕裂、阻塞读保证自动同步。这就是 05 章那句"队列解耦生产者和消费者"在工程里的兑现。

## [06] 软件定时器:周期采样滴答

Sensor 最初(04 章骨架)是在任务里用 `vTaskDelay(800ms)` 轮询采样的。06 章把它换成了**周期软件定时器** `SampleTmr` 驱动:定时器到期 → 回调跑 → 唤醒 Sensor → Sensor 采样。这一步的意义不在于"换了种等 800ms 的方式",而在于把"采样的节拍"从任务体里**外置**到了一个独立的节拍源——将来想改采样率、想让采样和别的节拍对齐、想加抖动,都只需要动定时器,不用改任务逻辑。

这里有个 06 章反复强调的红线必须守住:定时器回调跑在 timer 服务任务上下文,**绝不能阻塞、不能干长活**。所以 `prvSampleTimerCallback` 里只有极短的一行 `xSemaphoreGiveFromISR`(07 章改的)就返回,真正的采样工作留给被唤醒的 Sensor 任务。把"事件发生"和"事件处理"这样拆开,就是[软件定时器](../06_timers/)和[中断管理](../07_interrupts/)共同的"延迟处理"范式。

## [07] 中断管理:模拟按钮中断与 FromISR

07 章给 Sensor 增加了第二个唤醒源——**模拟"按钮中断"**。做法是新增一把二值信号量 `xButtonSemaphore` 和一个 2500ms 的"按钮源"定时器 `ButtonTmr`,回调里给这把信号量。同时把 06 章那个周期滴答从"任务通知"统一改成了 `xSampleSemaphore`(也走 `xSemaphoreGiveFromISR`),让两路中断事件的叙事一致——**都用信号量从类 ISR 上下文递交到任务**。

这里有一个 host 模拟绕不开的诚实交代:dashboard 里没有真中断,"按钮"和"滴答"都是软件定时器回调扮演的。为什么用定时器回调而不是从外部 pthread 直调 `*FromISR`?因为 POSIX port 下从外部 pthread 直调 `FromISR` 会 hang——这是[中断管理](../07_interrupts/)那章专门踩平的最大坑,也是[仿真坑点](../../pitfalls/)里的常驻条目。定时器回调跑在 timer 服务任务上下文,port 能正确跟踪这个上下文,所以从那里调 `FromISR` 是相对安全的。真硬件上把这两个回调换成真硬件定时器 ISR 和真按钮 GPIO ISR,内部那一行 give **一字不改**——这正是这套设计的教学价值:host 下学到的"ISR give 信号量、处理任务 take"这套延迟中断处理范式,原样搬到真硬件。

那个"主信号量短超时阻塞 + 旁路信号量零超时探一下"的写法,也是 07 章这段集成时为了绕开队列集 stall 而定的:它牺牲一点点按钮响应延迟(最长 50ms 窗口,人无感),换来稳定性。这个取舍在架构页讲过,这里不重复。

## [08] 资源管理:mutex 护共享计数

dashboard 里唯一真正需要上锁的资源,是那组被 Sensor / Display / Stats 三个任务并发访问的统计计数器。08 章的标准用法在这里完整落地:写方(Sensor、Display)take → 改 → give;读方(Stats)也 take → 拷整组快照 → give,然后**在锁外**慢慢 `console_print`。这个"锁只护拷三个字、不护慢 I/O"的写法是个重要的工程习惯——临界区越短越好,绝不能把 `console_print` 这种慢操作关在锁里,否则别的任务等锁等半天。

特意用**互斥量**(不是二值信号量)也是 08 章的明确选择:互斥量带优先级继承。dashboard 里 Stats 是最低优先级任务,它持锁读快照时若被 Sensor 抢、Sensor 又撞在这把锁上,Sensor 会把 Stats 临时抬到 `+3` 让它赶紧 give——这正是 08 章那个"优先级反转被破解"的演示,在 dashboard 这里它真在起作用、保护了 Sensor 的采样时序不被低优读方拖累。二值信号量没有这个机制,所以这里必须是 mutex。

## [09] 事件组:display 的 AND 组合门

事件组是 dashboard 给 Display 加的那道"初始化完成 AND 有新采样"的组合门。`xBootEvents` 上两位:`BIT_INIT_DONE`(Init 任务延时 1200ms 后 set,常驻不清)和 `BIT_NEW_SAMPLE`(Sensor 每投一帧 set,Display 消费一帧后手动 clear)。Display 的核心就一行 `xEventGroupWaitBits(INIT | NEW_SAMPLE, clearOnExit=pdFALSE, waitAll=pdTRUE)`,两个位**都**置位才往下走。

这里有个故意的设计值得点出来:`clearOnExit` 给的是 `pdFALSE`,然后手动 `ClearBits` 只清 `BIT_NEW_SAMPLE`、不动 `BIT_INIT_DONE`。这是因为 `xEventGroupWaitBits` 的 `xClearOnExit` 是"一刀切清掉所有等到的位",而我们要的是"只清新采样、保留初始化这道常驻门"——想精细控制哪个位清、哪个不清,就得手动 `ClearBits`。这就是[事件组](../09_event-groups/)那章讲的"按位清除"精细控制在工程里的兑现。把 `INIT_DONE_DELAY_MS` 故意设成 1200ms(大于采样周期 800ms),是为了让"AND 门阻塞"在运行输出里**肉眼可见**——Sensor 第一帧 800ms 就进了队列、也 set 了 `BIT_NEW_SAMPLE`,但 Display 因为 `BIT_INIT_DONE` 没到位一直阻塞,直到 1200ms 初始化完成才解锁。这个错位在[运行解读页](./03-running-and-extending.md)会亲眼看到。

## [10] 任务通知:带值的模式切换通道

任务通知是 dashboard 给 Sensor 加的**第三个**唤醒源——和前两路(周期信号量、按钮信号量)刻意区分开,演出它独有的卖点:**通知值能携带一个 32 位数据**。Control 任务每 1600ms 用 `xTaskNotify(Sensor, mode, eSetValueWithOverwrite)` 把一个模式码写进 Sensor 的通知值,Sensor 每轮 `ulTaskNotifyTake(pdTRUE, 0)` 零超时探一下,取到非零就切模式。

为什么这一路非用任务通知、不用前面那两把信号量?因为信号量只能 give/take 一下、**带不了"切到哪种模式"这个数据**。要是硬用信号量,你就得另开一条带外通道——一个全局变量存"当前要切到哪种模式" + 一个信号量通知"该切了",把"数据"和"通知"拆成两半,既啰嗦又埋下竞态窗口(读带外变量时模式可能又被改了)。任务通知把这个码直接塞进通知值,一次 `xTaskNotify` 就把"该切了 + 切到哪种"一起送达,这恰恰是[任务通知](../10_task-notifications/)区别于信号量的根本之处。`eSetValueWithOverwrite` 的覆盖语义还保证了"sensor 永远取到最新模式、不积压",适合控制类通信。

## [11] 低功耗:边界章,这里只是边界

[低功耗](../11_low-power/)是这套教程明确划在**教学边界外**的章——`configUSE_TICKLESS_IDLE` 在 host 模拟下能编能跑却测不出任何省电效果,因为 PC 是分时系统、不在乎功耗。dashboard 完成态没有引入 tickless idle 相关的机制,这里只是诚实标注:这一块在仪表盘的真实硬件版本里该考虑(host idle 时停 tick 省电),但 host 模拟下我们既不教也测不了。低功耗的机制和边界在 11 章正文里讲过,这一章不重复。

## [12] 调试:CpuStats 与运行时统计

dashboard 攒到这一步,常驻任务已经有七个了(再加内核 idle / timer daemon 共九个),一个自然的可观测性诉求冒出来:**它们各自吃多少 CPU?** 这正好演 `configGENERATE_RUN_TIME_STATS` 的看家本领。CpuStats 任务周期性用 `uxTaskGetSystemState` 拍一张全任务快照(每个 `TaskStatus_t` 里带 `ulRunTimeCounter`),算出占比打印。它呼应 04 章那张"状态快照"(state / prio / freestack)——[调试](../12_debugging/)那章补的就是"CPU 占用"这一列。

这里有两个工程细节是 12 章踩过的坑。一是 CpuStats 优先级压最低,否则它自己拍快照、格式化打印的那段 CPU 时间会被记进统计、把数据污染;二是它起手先睡一拍(4000ms),让别的任务先跑起来、积累一段运行时统计,否则第一张表全是 0% 没看头——这一点在运行输出里会亲眼看到(第一张 CpuStats 表打印的是 `(no run-time stats yet)`,第二张才有数)。这条"运行时统计需要先积累一段才准"的特性,是真硬件和 host 共有的,不是 host 边界。

## 小结:这张对照表

把上面十段收一张表,每个原语在 dashboard 里的角色一目了然:

| 章 | 原语 | 在 dashboard 里的角色 |
|----|------|---------------------|
| 03 | heap_4 + 2MB | 地基配置;HeapMon 周期探堆水位 |
| 04 | 任务切分 + 优先级 | Sensor(+3)/ Display(+2) 拆分,时序敏感者高 |
| 05 | 队列 | 容量 1 + `xQueueOverwrite` 的"最新值"主链路 |
| 06 | 软件定时器 | 周期 `SampleTmr` 驱动采样,回调极短不阻塞 |
| 07 | 中断(信号量) | 滴答/按钮两把信号量 + `FromISR`,延迟中断处理 |
| 08 | 互斥量 | `xStatsMutex` 护共享计数,优先级继承防反转 |
| 09 | 事件组 | Display 的"初始化 AND 新采样"AND 组合门 |
| 10 | 任务通知 | Control → Sensor 带值切模式(信号量做不到) |
| 11 | 低功耗 | 边界章,host 下不教不测,真硬件再考虑 |
| 12 | 运行时统计 | CpuStats 周期打印各任务 CPU 占用百分比 |

读完这张表你应该有那种"拼图最后一块归位"的感觉——前面十三章散落的原语,在这里每个都找到了自己的位置、各司其职、彼此协作,没有一个是"为用而用"的摆设。这就是集成章的意义。下一页我们跑一遍真实输出,看这些原语协作起来的样子,再聊聊往真硬件和更多功能上扩展时要注意什么。

# 项目实战：多任务传感器仪表盘

前面十三章我们是一个个原语往外抽的——先堆、再任务、再队列,一路加到事件组、任务通知、运行时统计,每章都配一个独立 demo 讲透单点机制,顺便往 `code/dashboard/` 那条脊柱里塞一块增量。这一章是那条脊柱的**完成态**:我们不再加新原语,而是退后一步,看这堆原语拼在一起、构成一个真实的多任务传感器仪表盘时长什么样。这不是新知识点,是**集成点**——你会看到为什么任务要这么切分、各原语之间如何协作、以及一个能跑的完整应用里那些"独立 demo 时各自正确"的原语,凑到一起时谁喂谁、谁等谁。

代码就是 `code/dashboard/main.c` 的当前态:七个应用任务(Sensor / Display / HeapMon / Stats / Init / Control / CpuStats)外加内核的 idle 与 timer daemon,中间串着一把采样队列、两把二值信号量、一把互斥量、一块事件组、一路任务通知,以及两个周期软件定时器。这一章不带新 demo——它本身就是前面所有 demo 的合体,所以我们把篇幅花在**讲清整体架构**和**运行输出的逐行解读**上。

## TL;DR

| 问题 | 一句话结论 |
|------|-----------|
| 这章是什么 | dashboard 脊柱的**完成态集成章**,把 03~13 的原语拼成一个能跑的多任务仪表盘 |
| 数据主链路 | sensor 采集 → `xQueueOverwrite` 进队列 → display 阻塞 `xQueueReceive` 取帧显示 |
| sensor 的唤醒源 | 三类:**周期滴答**(信号量,800ms)、**按钮事件**(信号量,2500ms)、**模式切换**(任务通知带值,1600ms) |
| 为什么 display 要等事件组 | "初始化完成 AND 有新采样"才刷屏——事件组的 AND 组合门 |
| 共享计数为什么上 mutex | sensor/display/stats 三个任务并发写同一组计数器,优先级继承防反转 |
| 怎么区分三类采样来源 | 输出里周期帧标 `periodic`、按钮帧标 `BUTTON!`、模式标 `mode=normal/BOOST` 一眼可分 |
| 可观测性 | HeapMon 看堆余量、Stats 看采样/显示计数、CpuStats 看各任务 CPU 占用百分比 |
| host 模拟的诚实边界 | "按钮/滴答"其实是软件定时器回调扮演 ISR;真硬件上把回调换成真 GPIO ISR,内部 give 一行不改 |

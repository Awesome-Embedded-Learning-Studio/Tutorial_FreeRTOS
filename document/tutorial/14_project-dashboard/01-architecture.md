# 整体架构:任务拓扑、数据流与唤醒源

这一章不带新原语,所以我们从最该先建立的那张**全景图**讲起:dashboard 里到底有几个任务、它们之间用什么连、谁唤醒谁。把这些关系在脑子里画出来,后面读 `main.c` 就不再是"一段段孤立的 API",而是"它们各就各位、各司其职"。这一页全在画这张图,代码细节留给[下一页](./02-how-primitives-fit.md)逐原语拆。

## 七个任务和两个定时器

dashboard 起来之后,系统里常驻的是**七个应用任务**加内核自带的两个(idle、timer daemon)。我们写的七个,按职责分大致是三组:一条**数据主链路**(Sensor → Display)、一组**可观测性任务**(HeapMon、Stats、CpuStats)、再加上**初始化**和**控制**两个配角。这些不是拍脑袋分的,而是顺着真实的工程诉求长出来的——主链路负责"采到数据并显示出来",可观测性负责"知道系统健康不健康",Init 和 Control 负责"在合适的时候开闸、在合适的时候切模式"。

两个**周期软件定时器**则扮演外部世界的节拍源:一个 800ms 的 `SampleTmr` 充当"采样滴答",一个 2500ms 的 `ButtonTmr` 充当"人按了一下按钮"。它们俩的回调都跑在内核那个 timer 服务任务上下文里,只做极短的一行 `xSemaphoreGiveFromISR` 就返回——也就是说,在我们这个 host 模拟里,**定时器回调就是 ISR 的替身**。这一点很重要,后面讲唤醒源时会反复用到:真硬件上这两个回调换成真硬件定时器 ISR 和真按钮 GPIO ISR,内部那一行 give 一字不改。这套"用定时器回调安全模拟中断源"的做法,是[中断管理](../07_interrupts/)那章专门踩平的坑,因为 POSIX port 下不能从外部 pthread 直调 `*FromISR`。

## 数据主链路:sensor → 队列 → display

整条数据链路其实只有三步,但它串起了好几个原语。Sensor 任务采到一帧,把帧塞进一个**容量为 1 的采样队列**;Display 任务在队列另一头阻塞 `xQueueReceive`,队列一有货就被唤醒、取帧、打印。这里有个刻意的选择是用了 `xQueueOverwrite` 而不是普通 `xQueueSend`——容量 1 的队列 + `xQueueOverwrite` 等于把队列当成一个"最新值寄存器":新采样永远覆盖旧的,Display 永远读到最新一帧、队列绝不积压。这种"最新值"语义和"一帧都不能丢"是两种相反的需求,我们在[队列管理](../05_queues/)那章对比过,这里采的是前一种,因为仪表盘的读者(人)只在乎当前值,不在乎中间漏掉了几帧。

链路里还插了一道**事件组的门**。Display 不是"队列一有货就立刻显示",而是先在一个事件组上等"初始化完成 AND 有新采样"两个位都置位(`xEventGroupWaitBits` 的 AND 等待)才往下走。Sensor 每投一帧就顺手 `SetBits` 一下"有新采样"位,一个 Init 任务延时 1200ms 后 `SetBits` 一下"初始化完成"位。这个 AND 门的意义是:**系统还没初始化好时,Display 就该老老实实阻塞、不要贸然刷屏**。为什么特意这么写?因为这是个很真实的需求——真硬件上显示驱动、外设初始化可能要花点时间,在那之前贸然操作显示是有风险的。事件组最擅长的就是这种"等多事件组合",具体机制见[事件组](../09_event-groups/)那章。

## 三个唤醒源:周期、按钮、模式切换

Sensor 任务是整个 dashboard 里唤醒源最丰富的一个,它被**三类完全不同的轻量唤醒手段**驱动,这一章把这三类刻意放在一个任务里对比,正是为了演出它们各自的适用边界。

第一类是**周期滴答**。800ms 的采样定时器回调给一把二值信号量 `xSampleSemaphore`,Sensor 在这把信号量上**带短超时阻塞**(50ms 一窗)——拿到就采一帧"周期帧"。第二类是**按钮事件**。2500ms 的按钮定时器回调给另一把二值信号量 `xButtonSemaphore`,Sensor 在每一轮结束前**零超时探一下**这把信号量,有就额外采一帧、输出里标 `BUTTON!`。这两把都是"无值的"信号量——它们只能表达"事情发生了",带不了任何数据。第三类是**模式切换**,这一路用的是**任务通知**而非信号量:一个 Control 任务每 1600ms 用 `xTaskNotify` 把一个模式码(`MODE_NORMAL` / `MODE_BOOST`)覆盖式写进 Sensor 的通知值,Sensor 每轮零超时探一下自己的通知值,取到非零就切模式、后续帧的 `mode=` 字段跟着变。任务通知和前两路信号量的根本区别就在于**它能携带一个 32 位值**——切到哪种模式这个"数据"直接跟着通知走,不用另开一条带外通道,这正是[任务通知](../10_task-notifications/)区别于信号量的卖点。

这里有个设计取舍值得点破。Sensor 同时要响应"周期"和"按钮"两个信号量,你可能会想用**队列集(Queue Set)**一把把两把信号量都挂上去、一次等待——这是教科书的标准做法。但我们在 POSIX port 下实测,"定时器服务任务里 `FromISR` + 队列集等待"这个组合会让定时器卡住(stall),是这套模拟的一个已知脆弱点。所以 dashboard 用的是更朴素的写法:**主信号量带短超时阻塞 + 旁路信号量零超时探一下**。它的代价是按钮事件最长延迟不超过那个 50ms 轮询窗口(人完全无感),换来的是稳如老狗。真硬件上队列集没有这个 stall 问题,完全可以改回队列集;这两条 host 边界在[中断管理](../07_interrupts/)和[仿真坑点](../../pitfalls/)里都有记录。

## 优先级分层:谁该先跑

`configMAX_PRIORITIES` 在我们这套配置里是 7,合法优先级 0~6。dashboard 把七个任务的优先级压成四档,分层逻辑很朴素——**谁更在乎时序,谁就更高**:

Sensor 给 `tskIDLE_PRIORITY + 3`,是应用任务里最高的,因为采样时序最敏感(周期滴答一到就该立刻采,不能被显示之类的活儿拖延);Init 也给 +3,跟 Sensor 同档,这看着反直觉,但道理是它一延时到点就该立刻 `SetBits` 把 Display 的 AND 门解锁,不被别的活儿拖延,所以也给了高优先级。Display 和 Control 都给 `+2`,低 Sensor 一档——显示是给人看的、不敏感;Control 只是"下一道模式指令就退"的短暂活儿,压在 Sensor 下面一档保证它绝不和 Sensor 抢采样时序。HeapMon、Stats、CpuStats 全压在最低档 `+1`,它们仨都是"只在有空时插进来读个快照/打个印"的可观测性任务,把它们的优先级压到最低,既保证了它们只在没有正经任务想跑时才占用 CPU,也避免它们自己拍快照、格式化打印的那点 CPU 时间去和主线抢。

这套分层背后有一条 FreeRTOS 调度的铁律在撑着:**只要高优先级任务没主动阻塞(让出 CPU),低优先级任务就一口都吃不到**。所以 Sensor 大部分时间 blocked 在信号量上、Display blocked 在事件组/队列上、那三个可观测性任务 blocked 在 `vTaskDelay` 上——它们各自让出 CPU 时,idle 任务才有机会吃满 100%(这一点在后面读 CPU 统计输出时会亲眼看到)。这条"高优先级任务必须主动让出、否则低优先级被饿死"是[任务管理](../04_tasks/)那章讲透的调度机制,在 dashboard 这里它是整套优先级分层能正常工作的前提。

## 共享资源:为什么计数要上锁

除了"谁唤醒谁",架构图里还有一条横切关系:**共享状态怎么保护**。dashboard 有一组统计计数器(总采样数、按钮采样数、总显示数),它被 Sensor、Display 两个任务并发写,还被 Stats 任务读。对 `uint32_t` 的 `++` 在 C 层面不是原子的(读-改-写三步,可能被抢占在中间),两个任务同时 `++` 会丢更新;读方如果"采到一半"还会读到几个计数器互相不一致的撕裂态。所以这一整组计数器用一把**互斥量** `xStatsMutex` 包起来:写方 take → 改 → give,读方(Stats)也 take → 拷整组快照 → give、然后在锁外慢慢打印。

这里特意用互斥量而不用二值信号量,图的就是它带的**优先级继承**:Stats 拿锁时若被 Sensor 抢、Sensor 又撞在这把锁上,Sensor 会把 Stats 临时抬到自己的高优先级、让它赶紧 give、自己早拿锁——这正是[资源管理](../08_resources/)那章演过的"优先级反转被优先级继承破解",在 dashboard 这里它是真在起作用的。整组计数器是 dashboard 里唯一需要上锁的资源,因为只有它真正被多任务并发读写;队列、信号量、事件组本身都是内核对象、内核已经保证安全,不需要我们再上锁。

## 把架构图画出来

把上面三张局部图(数据主链路、三个唤醒源、共享计数)叠在一起,就是 dashboard 的完整拓扑。文字描述一下:两个定时器(SampleTmr / ButtonTmr)在 timer 服务任务上下文里 give 两把信号量,把 Sensor 唤醒;Control 任务用任务通知给 Sensor 下发模式码;Sensor 采到帧后走一条"投队列 + set 新采样位 + 更新共享计数"的三连;Display 在事件组的 AND 门后面等"初始化完成 AND 有新采样",门开了就取帧、显示、更新共享计数;HeapMon / Stats / CpuStats 三个低优先级任务各自周期性地探一眼堆余量、读一份计数快照、拍一张全任务 CPU 占用快照。Init 任务跑完就自删,只留下一道常驻的 `BIT_INIT_DONE` 门。

这张图里每一个节点、每一条边,都对应前面某一章教过的一个原语——这就是为什么我们说这一章是"集成点"而非"新知识点"。下一页我们就按章序(03→12)把它们一个个对应回去,看每个原语在这个工程里**具体**扮演什么角色、为什么这么用。

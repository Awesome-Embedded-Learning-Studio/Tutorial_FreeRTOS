# 事件组

## 这章解决什么问题

前面攒下的同步原语各有地盘:队列传「数据」,二值信号量和任务通知传「一个事件」。但它们都是「一对一」的——一个发送者把一个东西递给一个接收者。真实系统里有一类需求是它们够不着的:**一个任务要同时等好几个互相独立的事件,而且这些事件之间是「并且」或者「或者」的关系**。比如等「网络就绪」**并且**「传感器就绪」**并且**「日志就绪」三件事都办妥了才开机;又比如等「有按键」**或者**「有网络包」**或者**「定时唤醒」三者之一就醒。这种「等多事件的组合」用队列、信号量、任务通知去拼,要么好几把信号量加轮询(丑且费 CPU),要么硬上队列集(啰嗦)。

**事件组(Event Group)**就是 FreeRTOS 给这类需求造的工具——一块大家共享的「布尔标志板」,任意多个任务都能 `set`、任意多个任务都能 `wait` 一个位的组合,setter 和 waiter 互不耦合。这一章把它的创建、置位、组合等待(AND/OR)、清除这一整套 API 讲透,并在 demo 里把「等多事件就绪」演给你看。

## TL;DR:核心结论

| 你想表达 | 该用谁 | 为什么 |
|---------|-------|-------|
| 传**数据**(尤其有序、要积压) | 队列 | 事件组不传数据,队列按值拷贝、有容量 |
| 发**单个事件**给单个任务 | 任务通知(更轻)或二值信号量 | 点对点、消费即消失 |
| 等**多个事件的组合**(AND/OR) | **事件组** | 一句 `xEventGroupWaitBits` 搞定,无需轮询 |
| 一个事件**广播**给多个等待者(一对多) | **事件组** | 位不被「取走」,所有 waiter 都能被唤醒 |

口诀:**传数据用队列,发单个事件给单个任务用信号量或任务通知(任务通知更轻),等多个事件的组合或广播给多个任务用事件组。** 事件组不传数据、不计数、不保证顺序,只擅长「等多事件组合」这一件事,但这件事它做得比谁都干净。它本身是纯软件机制,host 模拟和真硬件行为完全一致,没有 host 特有坑点。

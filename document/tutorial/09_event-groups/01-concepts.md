# 事件组概念:布尔标志板与组合等待

← 返回 [事件组](./index.md)

## 这章解决什么问题

到目前为止我们攒下的同步原语,各自都有一块擅长的地盘:队列传「数据」,二值信号量和任务通知传「一个事件」。但你仔细想会发现它们有一个共同的盲区——它们都是「一对一」的:一个发送者把一个东西递给一个接收者,接收者要么等到、要么没等到。可在真实系统里,有一类需求长这样:**一个任务要同时等好几个互相独立的事件,而且这些事件之间是「并且」或者「或者」的关系**。比如一个系统启动序列,要等「网络就绪」**并且**「传感器就绪」**并且**「日志子系统就绪」,三件事都办妥了才能宣布开机完成;又比如一个低功耗任务,要等「有按键」**或者**「有网络包」**或者**「定时唤醒」三者之一,任意一个发生就醒过来处理。这种「等多事件的组合」用队列、信号量、任务通知去拼,你会发现要么得用好几把信号量加一个轮询循环(丑且费 CPU),要么得硬上队列集(能用但啰嗦)。

事件组(Event Group)就是 FreeRTOS 专门给这类需求造的工具。你可以把它理解成**一块大家共享的「布尔标志板」**:板上有一排位(bit),每一位就是一个独立的事件标志,谁都能往板上 `set` 某一位(把某个事件标记为「发生了」),谁也都能在板上 `wait` 一个「这些位的组合条件」——`wait` 的时候你告诉它「我要等这几个位**全部**置位」(AND)或者「我要等这几个位**任意一个**置位」(OR),条件满足了它就把你唤醒,不满足你就老老实实 blocked 睡着、不占 CPU。这块板子的精妙之处在于它天然支持「一对多、多对一」:一个事件组可以被任意多个任务 `set`、被任意多个任务 `wait`,setter 和 waiter 互不认识、互不耦合。这一章我们就把事件组的创建、置位、组合等待、清除这一整套 API 讲透,并在 demo 里把「等多事件就绪」这套最常见的用法演给你看。

## 事件组是什么:一组布尔位 + 一个组合等待器

理解事件组,先把它和前几章的原语摆在一起做个对照。队列是「装一串数据、先进先出」,信号量是「装一个或几个 token」,任务通知是「塞一个值到一个任务私有信箱」——它们的共同点是**载体是「一个会变动的东西」**,你取走它就少一个。事件组完全不同,它的载体是**一组不会「被取走」的位**:每一位只是一个布尔标志,`set` 它就是把它写成 1,`clear` 它就是写成 0,**读它(等待它)并不会改变它**——除非你显式要求清除。这个差别决定了事件组天生适合「状态」而不是「消息」:你 set 了「网络就绪」这个位,十个任务来等它,它都还在那(只要没被清),十个任务都能被唤醒——这是「广播」语义;而信号量你 give 一个 token,只能唤醒一个 take 者,token 就被消费了——这是「点对点」语义。

在 FreeRTOS 里,一个事件组的位数取决于一个配置:`configUSE_16_BIT_TICKS`。如果是 8 位 tick(老习惯,资源极少的单片机),事件组有 **8 个可用事件位**;如果是 32 位 tick(我们这套 host 模拟用的就是它,`configUSE_16_BIT_TICKS=0`),事件组有 **24 个可用事件位**——多出来的高位被内核拿去做内部控制了。24 位对绝大多数应用绰绰有余,你用 `( 1 << n )` 这种写法来定义每一个事件位,比如 `#define BIT_NETWORK_READY ( 1 << 0 )`、`#define BIT_SENSOR_READY ( 1 << 1 )`,用起来就像在操作一组带名字的开关。

整个事件组的 API 非常精简,核心就四个:`xEventGroupCreate` 建一个事件组、`xEventGroupSetBits` 把某些位置 1、`xEventGroupWaitBits` 等一个位的组合(这是真正干重活的那个)、`xEventGroupClearBits` 把某些位清 0。外加一个 `xEventGroupGetBits` 只读地看一眼当前哪些位是 1(不清位)。我们接下来一个一个过。

## 创建与置位:xEventGroupCreate / SetBits

先建事件组。`xEventGroupCreate()` 不带参数,它会在堆上分配一个事件组对象(内含那 24 个事件位的状态 + 一条等待链表),返回一个 `EventGroupHandle_t` 句柄。和我们前几章建队列、建信号量一样,它**必须在进调度器之前创建好**,因为任务一启动就会去 `set`/`wait` 它,迟建的话它们第一次访问就撞上 NULL 句柄。建完记得用 `configASSERT` 兜一下分配失败(堆不够)的情况:

```c
/* 进调度器之前建好事件组,拿到句柄。 */
xBootEvents = xEventGroupCreate();
configASSERT( xBootEvents != NULL );
```

置位的写法更简单,`xEventGroupSetBits( xBootEvents, BIT_NETWORK_READY )` 就是把 `xBootEvents` 上的 `BIT_NETWORK_READY` 那一位写成 1。置位这个动作有一个很关键的性质需要你记住:**它是一次「广播」**。你 set 一位的瞬间,内核会去扫这个事件组上所有正在 `xEventGroupWaitBits` 阻塞的任务,逐个检查它们的等待条件有没有被这次置位满足,满足的就唤醒。所以 setter 完全不需要知道「现在有谁在等、在等什么」,它只管把事实摆上板子,内核替你通知。这就是事件组「松耦合」的精髓——产生事件的代码和消费事件的代码之间没有任何直接引用。

置位还有一个从 ISR 版本的姊妹函数 `xEventGroupSetBitsFromISR`,它和中断管理章讲的 `*FromISR` 系列同理:ISR 里不能直接调 `xEventGroupSetBits`(它内部可能唤醒多个任务、要做链表操作,不在 ISR 的安全范畴内),所以 FreeRTOS 提供了 `FromISR` 版——它内部其实是把「真正 set 位」这件事**转发给定时器服务任务代做**(deferred),从而避开 ISR 里的限制。本章的 demo 全程在普通任务上下文里 `set` 位,不涉及 ISR,所以用普通的 `xEventGroupSetBits` 就行;`FromISR` 版你先知道它存在、原理和延迟中断处理一致即可,真要用的时候翻中断章那套规矩照搬。

## 组合等待:xEventGroupWaitBits 的 AND 与 OR

`xEventGroupWaitBits` 是事件组最核心、参数也最多的 API,我们把它的五个参数逐个拆开讲,因为每个参数都在决定「我怎么等」。函数原型长这样:

```c
EventBits_t xEventGroupWaitBits( EventGroupHandle_t xEventGroup,
                                 const EventBits_t uxBitsToWaitFor,
                                 const BaseType_t xClearOnExit,
                                 const BaseType_t xWaitForAllBits,
                                 TickType_t xTicksToWait );
```

第一个参数 `xEventGroup` 不用说,在哪个事件组上等。第二个 `uxBitsToWaitFor` 是你**关心的那些位的掩码**——比如你关心「网络就绪」和「传感器就绪」两个位,就传 `BIT_NETWORK_READY | BIT_SENSOR_READY`;事件组上别的位(哪怕被别人 set 了)你压根不搭理。第三、四个参数是这章的两个灵魂:`xClearOnExit` 决定「成功返回时要不要清位」,`xWaitForAllBits` 决定「是 AND 还是 OR」。最后一个 `xTicksToWait` 是超时,传 `portMAX_DELAY` 就是死等。

`xWaitForAllBits` 这个参数就是 AND/OR 的开关。传 `pdTRUE` 是 **AND 等待**:`uxBitsToWaitFor` 里指定的位必须**全部**置位才返回,差一个都继续阻塞——这就是「等一组事件全部就绪」,本章 demo 的初始化同步就用它。传 `pdFALSE` 是 **OR 等待**:`uxBitsToWaitFor` 里指定的位**任意一个**置位就返回——这就是「等一组事件里任意一个发生」,典型用在「多路事件里谁先来我处理谁」的低功耗场景。这套 AND/OR 用一个布尔参数就切,是事件组最优雅的地方:你不需要为「等多个事件」写一堆 `if` 和轮询,一句 `xEventGroupWaitBits` 全搞定。

`xClearOnExit` 决定了「位是一次性的还是持久的」。传 `pdTRUE`:这次等待**成功返回**时,内核会**原子地**把 `uxBitsToWaitFor` 里那些满足条件的位清掉——注意是「读到并清掉」一气呵成,中间不会被别的任务插进来 set/clear,所以没有竞态。这个「消费即清除」的语义特别适合「事件是边沿触发的」场景:某个事件发生了、set 了位,你 wait 到它、顺手清掉,这样下一次同一个事件再发生、再 set,你又是一次全新的等待。传 `pdFALSE`:位**保持原样**,不清——适合「位代表一种持续的状态」或者「多个等待者都要看到这一位」的场景。这里有个常被忽略的细节:`xClearOnExit` 是**一刀切清掉所有等到的位**,做不到「只清这一个位、不清那一个位」;如果你要这种精细控制,就得传 `pdFALSE`、自己在返回后用 `xEventGroupClearBits` 手动只清你想清的那一位——本章 dashboard 增量正是这么干的,下面会展开。

返回值 `EventBits_t` 是「返回那一刻事件组的位快照」,它告诉你**到底是哪些位让你解除阻塞的**。这一点在和 OR 等待配合时尤其有用:OR 等待是「任意一个位就行」,但你醒来后往往想知道「到底是哪一个位先来的」,那就看返回值里哪些位是 1。另外,返回值也是你判断「我是被事件唤醒的、还是超时返回的」的依据:如果超时了,返回值里 `uxBitsToWaitFor` 那些位**一个都不会全到位**(AND 没全齐、OR 一个都没有),你拿返回值和你的掩码一比就分得清。

## 清除与读取:ClearBits / GetBits

`xEventGroupClearBits( xBootEvents, BIT_NEW_SAMPLE )` 把指定的位清成 0,它返回清之前的快照。它就是 `xClearOnExit=pdFALSE` 的配套:你选择不在 wait 里自动清,就可以在任意时刻手动清任意子集的位。`xEventGroupGetBits( xBootEvents )` 则是个只读的快照,告诉你当前哪些位是 1,它**不清位**,纯粹给你「看一眼」用——调试时特别方便,本章 demo 里就用它打印「清除之后位是不是真的归零了」来验证 `xClearOnExit` 的行为。

有一件事要专门提醒:**别在没有锁保护的情况下,用「GetBits 判断 + SetBits/ClearBits 修改」这套手动组合去模拟「等待」**。换句话说,别写「`while ( (xEventGroupGetBits(eg) & MASK) != MASK ) {}`」这种忙等循环——那是裸轮询、空烧 CPU,而且 GetBits 和判断之间有竞态。要等就用 `xEventGroupWaitBits`,它把「检查条件 + 不满足就阻塞 + 满足就(可选)清除 + 唤醒」这一整套做成了原子的、不占 CPU 的操作,这正是事件组相对裸标志位的全部价值。

## 何时用事件组,何时用别的:一道选择题

到这里你可能有个疑问:既然事件组这么灵活,干嘛不全用它、把队列、信号量、任务通知都换掉?答案在于**每个原语都是有「语义形状」的**,选错形状会给自己找麻烦。我们把四个原语放在一张决策表里来对一下。

什么时候用**事件组**:你要同步的是「多个独立事件的组合」(AND 或 OR),或者你要做「一个事件广播给多个等待者」(一对多)。事件组传的是「无数据的布尔事件」——它只告诉你「这件事发生了」,不告诉你「这件事的具体内容是什么」。所以如果你的事件本身不带载荷(比如「初始化完成」「有按键」「数据准备好了」这种纯信号),事件组是最贴的;如果你的事件还携带数据(比如「收到一个数据包,内容是 …」),那事件组就只能配一个队列用:事件组发「有包」的信号、队列传包的内容。

什么时候用**队列**:你要传的是「数据」,尤其是一串有序的数据(先进先出),或者你要做「生产者/消费者」的解耦。队列按值拷贝数据、有容量、能积压,这是事件组完全给不了的。一句话:**有数据要传 → 队列;只有信号要发 → 看下面。**

什么时候用**信号量**:你要做的是「一个事件通知一个任务」(二值信号量,经典的中断↔任务同步),或者「管理一组同质资源的配额」(计数信号量)。信号量是「点对点」的 token,give 一个 take 一个、消费即消失——它表达「请处理一下这件事」这种单次通知最自然。但一旦你的需求变成「等多件事的组合」或「一件事通知多个任务」,信号量就得好几把加轮询,这时事件组更合适。

什么时候用**任务通知**:它是「从一个任务发一个值/通知到另一个**特定**任务」的轻量通道,比信号量和事件组都更快、更省内存(它直接写进目标任务的控制块,没有独立对象)。但它有一个硬限制:**一发一收、点对点**,而且通知是目标任务私有的、别的任务等不到。所以任务通知适合「我明确知道要通知谁」的紧凑单点通信(比如 07 章那个「按钮」信号就完全可以用任务通知替代信号量);一旦你要「等多事件组合」或者「一个事件多任务都能收到」,任务通知就力不从心了,这时回到事件组。

把上面这堆浓缩成一句口诀:**传数据用队列,发单个事件给单个任务用信号量或任务通知(任务通知更轻),等多个事件的组合或广播给多个任务用事件组。** 下一章我们讲任务通知,会把它和信号量、事件组做一个更细的「同一件事三种写法」的对比,把这道选择题彻底讲死。

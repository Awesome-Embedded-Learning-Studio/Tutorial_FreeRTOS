# 互斥量、优先级反转与死锁:原理

> 本章拆成三篇:这一篇讲概念与原理(互斥量是什么、它和二值信号量的决定性区别、优先级反转怎么发生、死锁怎么预防);想直接看故障演出来的去 [独立 demo:复现反转,用互斥量破解](./02-priority-inversion-demo.md);想看这个能力怎么落进 dashboard 脊柱的去 [dashboard 增量:给共享统计计数上互斥量](./03-dashboard-mutex.md)。导航页在 [资源管理](./)。

## 这章解决什么问题

上一章我们把中断管理摊开了,学会了用信号量把「中断发生了」这件事从 ISR 安全地递交到任务。那一章里信号量扮演的角色是「通知」——ISR give 一把、任务 take 一把,核心是「事件同步」。这一章我们要用看起来几乎一样的 API,解决一个完全不同的问题:**多个任务都要碰同一块共享资源,怎么让它们不打架**。

问题来自一个很朴素的场景:dashboard 里 sensor 任务在写一组统计计数器(每采一帧就 `计数++`),display 任务也在写同一组计数器(每显示一帧也 `计数++`)。你可能觉得 `uint32_t` 的 `++` 能有什么事——但 `++` 在 C 层面根本不是一条不可分割的指令,它是「读出来、加一、写回去」三步。如果 sensor 刚把值读出来、还没写回去,就被更高优先级的任务抢走、那个任务又改了同一个变量,等 sensor 回来写回去的时候,中间那次修改就被「覆盖」丢了。这种丢更新在单任务裸机里不存在,在抢占式多任务里几乎是必然出现的——只要你跑得够久。我们需要一个机制,让「读改写」这三步变成一段**不可分割的临界区**:要么全做、要么全不做,中间谁也别插进来。这个机制就是**互斥量(mutex)**。

互斥量的 API 表面和上一章的二值信号量几乎一样——`xSemaphoreCreateMutex / xSemaphoreTake / xSemaphoreGive`,连 `SemaphoreHandle_t` 这个句柄类型都共用。但它们内核里的行为天差地别,这个差别就是本章真正的主角:**优先级继承**。我们会先亲手复现一个叫「优先级反转」的经典故障——全系统最高优先级的任务,被一个八竿子打不着的中等优先级任务活活饿死——然后看互斥量是怎么一行配置都不用改、就靠内核的优先级继承把它破解的。讲完反转,我们再补上资源管理里另一个必谈的雷区:死锁,以及它唯一靠谱的预防手段——固定加锁顺序。

## 互斥量:临界区的「钥匙」

互斥量的核心思想可以用「钥匙」来类比。一段共享资源(一个全局计数器、一个显示缓冲、一台共享打印机)配一把钥匙;谁要碰它,先 `xSemaphoreTake` 把钥匙拿到手——拿到的那一刻别人就只能在外头排队等;用完 `xSemaphoreGive` 把钥匙还回去,排在第一个的等待者就接过钥匙进去。同一时刻只有一个人拿着钥匙,所以「读改写」那段就不会被别人插队,这就是临界区。

我们直接看 API。创建用 `xSemaphoreCreateMutex`,它没有参数,返回一个句柄:

```c
SemaphoreHandle_t xMutex = xSemaphoreCreateMutex();
configASSERT( xMutex != NULL );   /* 堆不够会返回 NULL,生产代码必须查 */
```

拿到锁和归还锁长得和信号量一模一样,唯一要注意的是「拿不到怎么办」靠第二个参数——阻塞超时:

```c
/* portMAX_DELAY:拿不到就一直等下去(阻塞,不占 CPU)。
 * 也可以传 pdMS_TO_TICKS(100) 表示「最多等 100ms」,超时返回 pdFAIL。 */
xSemaphoreTake( xMutex, portMAX_DELAY );

/* ... 这中间就是受保护的临界区:放心地改共享资源,别人进不来 ... */

xSemaphoreGive( xMutex );   /* 出临界区必须 give,否则别人永远拿不到 */
```

这一对 `Take`/`Give` 必须严格配对、严格嵌套——进了几次就要出几次。互斥量内核会记住「当前是谁拿着我」,所以只有拿着锁的那个任务才能 `Give` 它(你手里没钥匙却想还钥匙,内核直接断言);二值信号量没这个限制,谁都能 give,这是两者一个隐藏但重要的差别。还有个 `configUSE_MUTEXES` 开关,模板里它是 1(开着),互斥量这套 API 才可用;如果哪天你为了省代码体积把它关成 0,链接器会把 `xSemaphoreCreateMutex` 整个剔掉。这一章我们开着。

## 互斥量 vs 二值信号量:长得一样,内核不同

到这里你肯定会问一个尖锐的问题:上一章的二值信号量也是 `Take`/`Give`,容量也是 1(「二值」嘛,要么有要么没有),拿来当锁用不也行吗?为什么要专门搞一个互斥量?答案是:**二值信号量能当锁,但它没有优先级继承,会触发优先级反转**。互斥量存在的全部理由,就是为了把优先级继承这个机制加进来。这是两者唯一、也是决定性的区别——API 层面长得像,是为了让你心智负担小;底层那一下「持锁者被抬优先级」,只有互斥量做。

还有几个次要差别顺带说一下,免得你以后踩。其一,二值信号量创建出来是「空」的(必须先 `Give` 一次让它变「满」,任务才能 `Take` 到),这是个经典初值坑;互斥量创建出来就是「满」的,可以直接 `Take`。其二,二值信号量谁都能 `Give`(典型的「ISR give、任务 take」用法),互斥量只能由持锁任务 `Give`,且通常不能在 ISR 里用互斥量(ISR 不能阻塞、也不持有任务上下文,拿互斥量没意义)——所以 ISR↔任务同步永远用信号量,任务↔任务互斥才用互斥量,这是选型上的一条硬规矩。其三,FreeRTOS 的互斥量还支持「递归互斥量」(`xSemaphoreCreateRecursiveMutex`),允许同一个任务把同一把锁 `Take` 多次、必须 `Give` 同样多次才解锁,适合一个任务里调了好几层函数、每层都要进同一把锁的场景;本章我们用普通的非递归互斥量就够。

## 优先级反转:最高优先级任务被无关任务饿死

讲优先级继承之前,必须先把它的「反派」——优先级反转——演清楚,否则你根本体会不到继承在干什么。优先级反转是这个剧本:有一个共享资源被一把锁保护着;一个**低优先级**任务先拿到了锁,正在慢吞吞地用着;这时全系统**最高优先级**的任务要来用这个资源,撞上锁、进 blocked 等锁释放——到这里都还正常,高优先级任务等低优先级任务干完,天经地义。真正的坑在下一步:此时一个**中等优先级**的任务就绪了,它根本不碰那个资源、纯粹是想跑自己的活,但它的优先级高于那个持锁的低优先级任务,于是调度器立刻把低优先级任务抢走、让中优先级任务独占 CPU。低优先级任务拿不到 CPU → 释放不了锁 → 高优先级任务拿不到锁 → 高优先级任务就一直 blocked 着,看着中优先级任务把自己的时间全耗光。**最高优先级的任务,被一个和这个资源毫无关系的中等优先级任务间接饿死了**——这就是「反转」:本该高优先级先享受 CPU,结果高优先级被低优先级拖着、被中优先级按住,优先级顺序整个倒过来了。

这个故障极其反直觉,也极其隐蔽:你的高优先级任务是「最高优先级」的,你检查任务优先级设置一点毛病没有,但它就是关键响应迟迟不来。新手的第一反应往往是「是不是我把优先级设错了」,反复调优先级都修不好——因为根因不在优先级设置,而在「保护资源的那把锁用错了类型」。

到底这个反转长什么样、互斥量的优先级继承又是怎么一行配置都不用改就把它破解的,下一篇 [独立 demo:复现反转,用互斥量破解](./02-priority-inversion-demo.md) 用真实输出讲给你看。

## 死锁:两把锁互相等

讲完反转,资源管理还有另一个必谈的雷区:死锁。死锁的经典画面是两个任务、两把锁,任务 A 拿了锁 1 还想要锁 2,任务 B 拿了锁 2 还想要锁 1,两边各持一把、又都在等对方手里那把,于是双双永久 blocked,谁也动不了。成因可以拆成四个同时成立的条件(互斥、持有并等待、不可抢占、循环等待),但对写代码的人来说,实用的认知就一条:**只要加锁顺序在多个任务之间不一致,就有死锁风险**。

举个最具体的例子。任务 A 的代码先 take 锁 1、再 take 锁 2;任务 B 的代码先 take 锁 2、再 take 锁 1。如果运气不好,A 拿到锁 1 的同时 B 拿到了锁 2,接下来 A 想拿锁 2 发现被 B 拿着、B 想拿锁 1 发现被 A 拿着,死锁。预防办法简单粗暴且唯一靠谱:**全系统所有任务,拿多把锁的顺序必须一致**。规定好「永远先锁 1 再锁 2」,那么 A 和 B 都会先去抢锁 1,谁先抢到谁一路拿下去,另一个在锁 1 上等着,不会出现「各持一把」的局面,循环等待这个条件就被打破了。

这套「固定加锁顺序」的纪律,从两把锁推广到 N 把锁、推广到「按某个全局序号从小到大加锁」,就是工业界防死锁的标准做法。还有几个实战要点值得记住:临界区要尽量短——拿到锁、干完那几行共享资源的活、立刻 give,绝不要在锁里做慢操作(尤其是 I/O、`console_print` 这种),否则既放大反转风险、又拉长别人等锁的时间;能用「在锁里只拷一份快照、出锁再慢慢处理」的写法,就别把整个处理过程关在锁里(本章 dashboard 的统计任务就是这么写的,下一篇 [dashboard 增量](./03-dashboard-mutex.md) 你会看到)。另外互斥量的 `Take` 最好带上合理的超时而不是无限等——万一代码有 bug 真死锁了,带超时的版本至少能返回 `pdFAIL`、让你有机会打日志或走恢复路径,而不是整个任务永远冻住。优先级继承能破反转,但它**救不了死锁**——死锁是逻辑上的循环等待,不是优先级问题,所以加锁顺序这条纪律必须靠你自己守。

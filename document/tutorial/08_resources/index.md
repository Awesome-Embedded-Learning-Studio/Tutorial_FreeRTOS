# 资源管理

## 这章解决什么问题

上一章我们用信号量做「中断→任务」的事件同步;这一章用长得几乎一样的 `xSemaphoreCreateMutex / Take / Give` 解决一个完全不同的问题:**多个任务都要碰同一块共享资源,怎么让它们不打架**。一个 `计数++` 在抢占式多任务里根本不是一条不可分割的指令(读→加→写三步),sensor 和 display 并发改同一个变量迟早丢更新——我们需要一个把「读改写」包成不可分割临界区的机制,这就是**互斥量(mutex)**。互斥量表面和上一章二值信号量几乎一样,但内核里的**优先级继承**是两者唯一、也是决定性的区别,本章真正的主角就是它。

## TL;DR:关键结论

| 点 | 一句话 |
|------|--------|
| **互斥量** | `xSemaphoreCreateMutex` 创建、`Take` 拿、`Give` 还,严格配对嵌套,只有持锁任务能 give,把「读改写」包成不可分割临界区 |
| **mutex vs 二值信号量** | 唯一决定性区别是**优先级继承**——二值信号量没它、会触发反转;API 长得像只是为减小心智负担 |
| **优先级反转** | 最高优先级任务被一个和资源无关的中等优先级任务**间接饿死**(demo 里 High 等了 2800ms),根因不在优先级设置、在锁类型 |
| **优先级继承** | 持锁者被有高优先级任务等锁时**临时抬**到高优先级,不受中优干扰地尽快还锁(High 等待 2800ms→960ms),一行业务代码都不用改 |
| **死锁** | 加锁顺序不一致构成循环等待,**优先级继承救不了它**;唯一靠谱预防是全系统固定加锁顺序 + 临界区尽量短(锁里只拷快照、出锁再处理) |
| **选型硬规矩** | ISR↔任务同步用信号量,任务↔任务互斥才用互斥量(互斥量不能在 ISR 里用) |

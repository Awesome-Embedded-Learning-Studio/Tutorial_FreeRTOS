# Tickless Idle 的机制:让 CPU 睡得更沉、醒得更少

> 低功耗章第一页。这一页把 tickless idle 的机制从头到尾拆给你看——它的开关、内核空闲任务走上哪条新路径、真正省电的脏活在哪个 port 宏里。下一页 [打开 configUSE_TICKLESS_IDLE 的独立 demo](./02-tickless-demo.md) 用一个能编能跑的 demo 把「机制在跑、host 上 tick 没停」演出来。

## 这章解决什么问题

前面十章我们关心的全是「正确性」——任务怎么切、队列怎么传、信号量怎么同步、中断怎么处理。这一章换一个完全不同的轴:**功耗**。在电池供电的嵌入式设备里(一个跑纽扣电池十年的传感器、一个穿戴、一个无线标签),CPU 每多醒一毫秒、每多跑一条指令,都是真金白银地从电池里抠走的电量。所以嵌入式工程师有一整套和「让 CPU 尽量睡、尽量少醒」相关的工程实践,FreeRTOS 也专门为此提供了一个机制,叫 **Tickless Idle(无滴答空闲)**。这一章我们要搞清楚的就是:这个机制在真 MCU 上到底是怎么省电的、它打开之后内核的空闲任务会多走哪条路、以及——必须立刻诚实说清楚的——为什么在 host 模拟下我们只能讲清楚它的**机制**,却**测不出任何真实的省电效果**。

这一章是本教程最「边界感」的一章,没有之一。坦白讲:如果你翻开这一章是冲着「我想在 PC 上看到省了多少毫安」来的,那你会失望——因为这个数字在 host 上根本不存在,我们在 [教学边界](../01_why-rtos/) 里早就把功耗声明为「host 模拟教不了」的三件事之一(另两件是实时性、中断延迟)。但这不代表这一章是空的。恰恰相反,我们要做的是一件更扎实的事:把 tickless idle 的机制从头到尾拆给你看,让你彻底理解「空闲任务打开这个开关后会走上一条什么样的路径、真 MCU 的 port 在那条路径里干了什么」,这样等你移到真硬件上时,你知道这个开关在做什么、该不该开、开了要当心什么。机制是真的、可移植的;省电数字是边界外的、本教程不给的。这两件事我们分得清清楚楚。

## 先理解:CPU 闲着的时候,功耗都花在哪

要理解 tickless idle 省的是什么,得先看清「CPU 空闲」这件事在裸机和 RTOS 上分别长什么样。一个跑着 super-loop 的裸机程序,它的 `while(1)` 主循环里几乎总是空的——没有事做的时候,它要么在那儿死循环空转(忙等,把一个核占满、电流拉满),要么写一个 `__WFI`/`__WFI` 指令让 CPU 进一个浅睡状态等下一个中断。FreeRTOS 把这件事标准化了:只要调度器发现**没有任何就绪任务可跑**(所有任务都在 blocked/suspended),它就切到一个内核自带的「空闲任务」(idle task,优先级 0)。这个空闲任务什么都不干,它的存在意义就是「给调度器一个可以永远跑的最低优先级任务」,让 CPU 在没活儿的时候有个落脚点。

问题就出在这个「落脚点」上。默认情况下,FreeRTOS 的 tick 中断是**永不停歇**的——哪怕系统里所有任务都在睡、只剩空闲任务在空转,tick 中断每过一个 tick 周期(比如 1ms)还是会准时响一次,把空闲任务打断、走一遍调度逻辑(发现还是只有空闲能跑)、再回空闲任务继续转。这一个 tick 周期里,CPU 从浅睡被 tick 中断唤醒、跑了一堆「发现没活儿」的判断、又睡回去——而那一堆判断其实屁用没有,因为下一个真正需要 CPU 的任务解除阻塞,可能在一秒、十秒之后。换句话说:**默认的 FreeRTOS,在系统空闲时,仍然每 1ms 被 tick 中断「无意义地」唤醒一次**,这一来一回的唤醒和判断,就是白白烧掉的电。tickless idle 要省的,正是这部分。

## Tickless Idle 的核心思想:没活儿就别叫醒我

Tickless Idle 的思路一句话就能说完:**既然下一个真正需要 CPU 的事件(某个任务的 `vTaskDelay` 到期、某个队列等到数据)还在很远的将来,那这段时间里,与其每 1ms 被 tick 中断无意义地唤醒一次,不如干脆把 tick 整个停掉、让 CPU 进更深的低功耗模式,只配一个低功耗定时器在「下一个事件该发生」的那个时刻把我唤醒。** 这就是「tick-less」——tick 更少,因为该停的时候它真的停了。

具体到内核里,这套机制是怎么落地的?关键是一个配置宏 `configUSE_TICKLESS_IDLE`。你把它设成 1,内核的空闲任务代码里就多走一段逻辑(在 `tasks.c` 的 `prvIdleTask` 里)。这段逻辑干三件事:第一步,它调一个内部函数 `prvGetExpectedIdleTime()` 算出「预计还能空闲多久」——这个值就是「下一个任务解除阻塞的时间」减去「当前 tick」,换句话说,就是「到下一件正经事发生之前,还有多少个 tick 的空窗」。第二步,如果这个预计空闲时间大于等于一个门槛 `configEXPECTED_IDLE_TIME_BEFORE_SLEEP`(默认 2 个 tick),它才觉得「值得睡」——空窗太短就别折腾了,进进出出低功耗的开销比省下的还多。第三步,值得睡的话,它挂起调度器(`vTaskSuspendAll`)、然后调用一个 port 提供的宏 `portSUPPRESS_TICKS_AND_SLEEP(预计空闲时间)`,真正的「关 tick、进低功耗、配唤醒」的脏活全在这个宏里。

到这里机制就讲完了,但最关键的那个宏 `portSUPPRESS_TICKS_AND_SLEEP` 是 port 负责实现的——它的具体内容**完全取决于你跑在什么硬件上**。这正是理解这一章边界的钥匙,我们下一节专门拆它。

## portSUPPRESS_TICKS_AND_SLEEP:真 MCU 上省电全靠它,host 上它是个空壳

`portSUPPRESS_TICKS_AND_SLEEP` 这个宏是 tickless idle 的「省电发动机」,它接到「预计空闲多少 tick」这个参数,负责把这段时间尽可能省下来。在一个真 MCU port 上(比如 FreeRTOS 官方的 `GCC/ARM_CM3`、`GCC/ARM_CM4F`、`RP2040` 这类),这个宏的实现大致长这样:先把 tick 中断关掉(别让它每 1ms 来烦我),配一个硬件低功耗定时器(或者复用某个已有的定时器)让它在「预计空闲时间」到点时产生一次中断,然后执行一条让 CPU 进低功耗模式的指令(ARM 上通常是 `WFI`/`WFE`,进的是 wait-for-interrupt 状态,时钟可以降频甚至停掉一部分外设)。CPU 就这么一直睡,直到那个低功耗定时器的中断、或者任何一个别的中断(串口、GPIO 按键)把它唤醒。醒过来之后,port 会根据「实际睡了多久」把内核的 tick 计数补上(因为 tick 中断停了,tick 没在走,得手动把丢掉的 tick 补回来,让 `xTaskGetTickCount()` 仍然是准的),再恢复 tick 中断、恢复调度器,系统继续跑。这一进一出,CPU 真的少醒了成百上千次,电流真的降下来了——这就是真硬件上 tickless idle 省电的全部奥秘,它省的不是「算得快」,而是「睡得沉、醒得少」。

那么 host 模拟呢?这就到了这一章最该诚实的地方:**POSIX port 压根没有定义 `portSUPPRESS_TICKS_AND_SLEEP` 这个宏**。FreeRTOS 的头文件 `FreeRTOS.h` 里对它有一行兜底:`#ifndef portSUPPRESS_TICKS_AND_SLEEP` / `#define portSUPPRESS_TICKS_AND_SLEEP( x )`——一个**什么都不做的空宏**。也就是说,我们在 host 上打开 `configUSE_TICKLESS_IDLE=1`,内核的空闲任务确实会老老实实走完前面那套「算预计空闲、判门槛、挂起调度器」的逻辑,但走到最关键的 `portSUPPRESS_TICKS_AND_SLEEP()` 这一步时,它撞上的是个空壳——什么都没发生,tick 中断照常每 1ms 跳一次,CPU 照常在跑(真正让它「歇会儿」的是我们 app_hooks.c 里那个 idle hook 的 `usleep`,那跟 tickless idle 毫无关系,只是别把 PC 的一个核占满而已)。

为什么会这样?因为「关 tick、进 WFI、配低功耗定时器」这一整套操作,**每一个都是和具体 MCU 硬件寄存器死绑定的**——它要去碰 SysTick 寄存器、去碰某个低功耗定时器的外设、去执行一条只有 ARM/RISC-V 内核才认的 `WFI` 汇编指令。这些在 PC 的 Linux 上既不存在、也毫无意义(PC 的 CPU 功耗被操作系统管着,你的程序去 `WFI` 也只是个普通指令,不会触发任何省电;而且 PC 根本不靠电池跑、不在乎这点功耗)。POSIX port 的作者干脆就不实现这个宏,留个空壳。这不是 POSIX port 的缺陷,是它的**职责边界**——它的目标是「让你在 PC 上学内核调度/同步机制」,功耗压根不归它管。所以「host 模拟下 tickless idle 看不见省电」不是 bug,是设计如此;我们在 [教学边界](../01_why-rtos/) 和 [仿真坑点](../../pitfalls/) 里反复声明的那条「功耗是边界外」,在这里有了最具体的落地。

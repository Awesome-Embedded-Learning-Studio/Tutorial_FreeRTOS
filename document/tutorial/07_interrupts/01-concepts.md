# 中断的概念:ISR 与任务上下文、FromISR API、host 模拟的雷

> 中断章第一页,讲概念和原理。这一页结束时,你会清楚 ISR 这套规矩、ISR↔任务同步的经典模式,以及 host 模拟下「为什么不能瞎假装中断」。下一页 [独立 demo:延迟中断处理](./02-deferred-isr-demo.md) 把这些概念演成能跑的代码。

## 这章解决什么问题

前面几章我们讲的所有原语——任务、队列、软件定时器——都跑在一个共同的前提上:它们都是**任务上下文**里的东西。任务想睡就 `vTaskDelay`、想等队列就 `xQueueReceive` 死等、想发通知就 `xTaskNotifyGive`,这些 API 都有一个隐含的假设——你是在一个普通的、被调度器正常管理的任务里调它们。但嵌入式系统里还有另一类完全不同的执行上下文:**中断服务程序(ISR)**。串口收到一个字节、定时器溢出、按键被按下、DMA 传完一轮,硬件都会异步地打断 CPU,跳进你写的中断处理函数去跑一段。这一章要回答的问题就是:ISR 这个特殊上下文,和任务上下文到底有什么不一样?ISR 里能用哪些 API、不能用哪些?ISR 想把「我这件事发生了」告诉一个任务、让任务去处理,最干净的做法是什么?

这是整个教程里 host 模拟最棘手、也最需要「诚实交代边界」的一章,因为真相是:**POSIX port 没有真正的中断**。我们没法在一台 PC 上真发一个硬件中断让 FreeRTOS 去响应。所以这一章我们要做两件事:第一,把真硬件上 ISR 的规矩、中断↔任务同步的经典模式讲透——这部分在 host 和真硬件上逻辑完全一致;第二,诚实地讲清 host 模拟下我们「用什么安全的办法假装有中断」,以及为什么不能瞎假装(从外部 pthread 直调 FromISR 会直接 hang)。把这两件事分清,你在这章带走的就是一套「搬到真硬件上一行不用改」的中断处理写法。

## ISR 不是普通任务:它有三条硬规矩

理解中断管理,起点是认清 ISR 这个上下文和任务上下文的三点本质差别,这三点差别直接决定了 ISR 里能干什么、不能干什么。

ISR 是被**硬件异步抢占**调进来的,它没有自己的任务控制块、不归调度器按优先级轮转,它是「插队」执行的。这意味着它一进来,被打断的那个任务就得乖乖等着,直到 ISR 返回才能继续。所以第一条规矩是:**ISR 必须极快返回**。你在 ISR 里耗的时间越长,整个系统对别的中断、对任务的响应就越迟钝——这叫中断延迟(latency)被你亲手拉高。真硬件上有些中断延迟是硬指标(比如电机控制要求几十微秒内必须响应),你在 ISR 里磨蹭,系统就废了。所以 ISR 的铁律是「只做最必要的事,立刻返回」,把真正耗时的活儿丢出去交给任务做——这套做法有个专门的名字,叫**延迟中断处理(deferred interrupt handling)**,也就是本章 demo 的主角。

第二条规矩是:**ISR 里绝不能阻塞**。不能 `vTaskDelay`、不能在空队列上死等、不能拿互斥量。原因很直接:vTaskDelay 这类函数的语义是「把当前任务挂到延时列表上、切到别的任务」,但 ISR 压根不是任务,调度器没有它的「任务状态」可挂;如果 ISR 调了阻塞函数,调度器会试图去操作一个不存在的任务上下文,直接乱套。互斥量更糟——互斥量阻塞时会涉及优先级继承,而 ISR 没有可被继承的优先级。所以 FreeRTOS 干脆规定:ISR 上下文里禁止调用任何可能阻塞的 API。

第三条规矩,也是这一章的核心 API 知识点:**ISR 里只能用带 `FromISR` 后缀的 API**。你在前几章用惯的 `xQueueSend`、`xSemaphoreGive`、`vTaskNotifyGive`,这些是「任务上下文版」;ISR 里要用的是 `xQueueSendFromISR`、`xSemaphoreGiveFromISR`、`vTaskNotifyGiveFromISR`。为什么非要分两套?因为任务版函数内部会做「我现在在任务上下文吗?」「我该不该现在就触发一次任务切换?」这类检查和动作,这些动作在 ISR 里既不安全(查上下文的方式对 ISR 不成立)、也无意义(中断退出时本来就有一个统一的切换点);FromISR 版本为中断上下文专门重写了逻辑:不查上下文、不自己切任务,而是把「需不需要切换」这个信息通过一个出参告诉调用者,由调用者在 ISR 末尾统一处理。所以「ISR 里只能用 FromISR」不是风格建议,是硬性要求——你用错版本,要么断言炸、要么行为错乱。

## 二值信号量:ISR 告诉任务「事件来了」的最经典工具

ISR 受了这三条限制,那它怎么把「我这件事发生了」通知一个任务、让任务去干活?最经典、也最直观的工具就是**二值信号量(binary semaphore)**。二值信号量你可以理解成「一个只能装一个 token 的信箱」,它的状态只有两种:要么「有 token」(满)、要么「没 token」(空)。ISR 在类中断上下文里调 `xSemaphoreGiveFromISR` 往信箱里塞一个 token——这就是「事件来了」这个动作;另一边,处理任务在 `xSemaphoreTake` 上阻塞死等,平时它 blocked、不占 CPU,一旦信箱里有了 token,它就被唤醒、取走 token、然后去干真正的活。

这套「ISR give、任务 take」的模式,就是延迟中断处理的标配写法。它的精妙之处在于分工明确:ISR 里只做一件极短的事(give 一下、立刻返回),把中断延迟压到最低;真正耗时的工作——读缓冲、组数据、发队列、调 printf——全部在处理任务的普通任务上下文里做,没有任何 ISR 的限制。处理任务想阻塞就阻塞、想用任何 API 都行,因为它跑在任务上下文。你看,前几章我们学的队列、信号量、任务通知这些原语,在「中断→任务」这个场景下,信号量恰好是最贴切的那一个——它表达的就是「一个事件发生了、请处理一下」这种纯粹的通知语义,不携带数据(数据你可以另外用队列传)。

顺带说一句,信号量还有个「计数」版本叫**计数信号量(counting semaphore)**,它和二值信号量的差别是信箱能装不止一个 token——`xSemaphoreCreateCounting(最大值, 初值)`。它适合两类场景:一是「统计事件积压」,比如中断发生得比处理任务消费得快,你想知道到底积了多少个没处理,就用计数信号量逐个 give、处理任务逐个 take,计数值就是积压数;二是「管理一组资源」,比如有 3 个发送通道,初值给 3,每用掉一个 take 一个、用完 give 回去。本章 demo 只用二值信号量(通知语义足够),计数信号量后面用到再展开,你知道它存在、是二值的「可装多个 token」版本即可。

## portYIELD_FROM_ISR:让被唤醒的任务尽快上 CPU

讲完 give/take 的配合,还有最后一个细节,就是 `portYIELD_FROM_ISR` 这个宏是干嘛的。设想一下:ISR give 了信号量,处理任务被唤醒(从 blocked 变成 ready),但此刻正在跑的是被中断打断的那个低优先级任务。处理任务虽然优先级更高、现在是 ready,可它不会马上跑——得等下一次正常的调度点。如果被打断的任务正好是个长任务,处理任务就要干等它跑完才能轮到,中断响应就被拖了。`portYIELD_FROM_ISR` 就是用来在「中断退出」的那一刻强制做一次调度:如果刚才那次 give 唤醒了一个比当前任务更高优先级的任务,就请调度器在中断返回时直接切到它,而不是回到被打断的那个任务。

用法是标准的三步。你给 FromISR 函数传一个 `BaseType_t` 变量的地址当第二参数(叫 `xHigherPriorityTaskWoken`),先把它初始化成 `pdFALSE`;调 `xSemaphoreGiveFromISR(sem, &xHigherPriorityTaskWoken)`,如果这次 give 唤醒了高优先级任务,函数会把它写成 `pdTRUE`;最后调 `portYIELD_FROM_ISR(xHigherPriorityTaskWoken)`——它内部会判断,如果是 `pdTRUE` 就在中断退出时切任务,否则什么都不做。这套「给 woken 出参、末尾按需 yield」就是 FromISR API 区别于任务版 API 的核心机制:它把「要不要切任务」的决定权延迟到 ISR 末尾统一做,而不是 give 的时候自己贸然切。本章 demo 会把这三步完整写一遍。

## ⚠️ host 模拟最大的一颗雷:不能从外部 pthread 直调 FromISR

到这里概念都讲完了,但轮到 host 模拟落地时,我们会撞上这章最大的一颗雷,也是必须诚实交代清楚的边界:**POSIX port 下,你不能从一段外部 pthread(不归 FreeRTOS 调度器管的线程)里直接调 `*FromISR` API,调了就会死锁(hang)**。这颗雷的根因在 POSIX port 的实现里:它把每个 FreeRTOS 任务映射成一个 pthread,任务之间的切换靠 `SIGUSR1`/`SIG34` 这一类信号在 pthread 间同步(相当于用信号来模拟「触发一次上下文切换」);而 `*FromISR` 这套函数内部假设「我现在正处在一次被 port 正确跟踪的中断里」,它会去碰 port 的中断嵌套计数、去发调度信号。如果你在一个 port 根本不知道的 pthread 里调它,这个计数和信号就全乱套了——典型表现就是程序卡死在某次 give 上再也回不来,debug 起来极其折磨,因为没崩溃、没断言,就是 hang。这条坑在仿真坑点章的「ISR API hang」条里有专门记录,务必对照看一遍。

那 host 模拟下我们怎么「假装有中断」?关键是找一个 **port 正确跟踪的上下文**来扮演 ISR。最常用、最安全的两个落点是:**软件定时器回调**和 **tick hook**。软件定时器回调(上一章讲过)跑在内核自动建的「定时器服务任务」(daemon task)上下文里——它是一个正经的 FreeRTOS 任务、被 port 正确管理;tick hook 跑在每次 tick 中断的处理里——POSIX port 把 tick 也实现成了一段被跟踪的中断路径。从这两个上下文里调 `*FromISR`,port 不会错乱,不会 hang。换句话说,在 host 模拟下我们让「软件定时器回调」或「tick hook」来**扮演真硬件上 ISR 的角色**:它们都满足 ISR 的那个核心特征——「被异步调进来、必须极快返回」——于是它们就成了我们演练延迟中断处理的安全舞台。

但我们要彻底诚实:这**不是真中断**。软件定时器回调不是被硬件抢占的,它是由定时器服务任务依次调度出来的,它的「即时性」受服务任务何时被调度影响,不具备真硬件 ISR 那种「打断一切、立刻执行」的确定性延迟。host 模拟下没有中断延迟可言(这在教学边界章就声明为边界外了)。所以本章我们演示的是延迟中断处理的**模式和信号量用法**,这套模式搬到真硬件上,只要把「定时器回调里的 `xSemaphoreGiveFromISR`」换成「真 ISR 里的 `xSemaphoreGiveFromISR`」,其余代码一行不用改。模式是真的、可移植的;只是 host 下「触发它」的那个上下文是个替身。

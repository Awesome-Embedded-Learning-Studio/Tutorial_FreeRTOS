# 队列的概念:传送带、按值拷贝、阻塞读

> 队列章第一篇。这一篇把队列三个核心 API 的语义讲透——传送带结构、按值拷贝、阻塞读与超时。概念过完,下一篇 [阻塞与超时的独立 demo](./02-blocking-demo.md) 把这些行为用肉眼可见的输出演给你看。

## 这章解决什么问题

上一章我们把 dashboard 从单任务拆成了 sensor 采集任务和 display 显示任务,但在两任务之间传递数据的手段,是一根**裸的全局变量** `g_xLatestSample`。那一章我特意埋了个伏笔:这根全局变量「在单写者+单读者、读写基本原子」的场景下侥幸能用,但留下了隐患。这一章就是来把那根隐患拔掉的——我们要用队列(QUEUE)替代全局变量,让任务之间的数据传递既正确又优雅。

先说清全局变量到底差在哪儿。你可能觉得「sensor 写、display 读,不就一个 `int` 吗,能出什么事」,事情恰恰出「觉得」上。第一,一旦传递的不是一个 `int` 而是一个结构体(几个字段凑一块),写者写到一半、读者来读,就会读到「半新半旧」的撕裂帧——`ulSeq` 是新的、`lValue` 还是旧的,这种 bug 极难复现、极难定位。第二,全局变量本身**不带任何「通知」能力**:display 怎么知道 sensor 什么时候写好了新值?要么 display 拼命轮询(浪费 CPU),要么靠 `vTaskDelay` 盲等(既不及时、又会漏掉采集事件)。这两个问题——数据完整性和到达通知——靠全局变量都得你自己手搓,而队列把它们一次都解决了。

队列是 FreeRTOS 里最通用、最值得吃透的任务间通信原语。你可以把它理解成一根**线程安全的、带阻塞通知的环形传送带**:一头往里塞东西,另一头往外取东西,内核在背后帮你管好并发、帮你管好「取的时候要是空的就睡着等」。这一章我们会把它的三个核心 API(`xQueueCreate` / `xQueueSend` / `xQueueReceive`)、它最值钱的能力(阻塞与超时)、以及它一个容易踩坑的语义(消息按值拷贝)挨个讲透,然后在一个独立 demo 里把「阻塞读」和「超时返回」两件事亲眼演出来,最后把这套能力嫁接到 dashboard 上,让 sensor 把采样数据经队列发给 display。

## xQueueCreate:一根传送带是怎么搭起来的

创建队列就一个 API,签名极简:

```c
QueueHandle_t xQueueCreate( UBaseType_t uxQueueLength,
                            UBaseType_t uxItemSize );
```

它干的事是:从堆里 `pvPortMalloc` 一块内存,内部搭起一个容量为 `uxQueueLength` 个槽位、每个槽位 `uxItemSize` 字节的**环形缓冲区**,再附上一套管理它的元数据(头尾指针、当前元素数、等待这个队列的任务链表),最后返回一个不透明句柄 `QueueHandle_t`。两个参数的含义值得展开。

第一个 `uxQueueLength` 是队列能装下几条消息。这个值是你在「积压容忍度」和「内存开销」之间的取舍:队列越长,生产者短时间狂发也不怕丢(消费者慢慢取),代价是占用更多堆内存(`uxQueueLength × uxItemSize` 字节加上每条消息少量开销);队列越短,内存省,但一旦生产者比消费者快、队列满了,新消息就塞不进去。队列到底多大合适,取决于你的场景有没有「允许丢消息」——后面讲 dashboard 增量时会专门对比两种语义。

第二个 `uxItemSize` 是每条消息多大。这里有个新手常犯的错:把它理解成「消息的指针大小」就错了。**`uxItemSize` 是消息本身的大小,不是指针大小**。队列内部不会帮你存指针、再让你自己去解引用——它会在创建时按 `uxItemSize` 把每条消息的内容**原样拷贝**进自己的缓冲区。这直接引出队列最核心的一个语义,值得单独成节。

还有一点容易忽略:`xQueueCreate` 内部要 `pvPortMalloc`,所以它和 [任务管理](../04_tasks/) 那章讲的一样,吃的是 [堆内存管理](../03_memory/) 那章搭好的堆——`uxQueueLength × uxItemSize` 加上队列控制块,全从 `configTOTAL_HEAP_SIZE` 里出。如果堆不够,`xQueueCreate` 返回 `NULL`。所以创建队列之后检查返回值是个好习惯,创建失败这种致命错误一般直接断言掉(本教程的 demo 就是这么做的)。另外,**队列必须在进 scheduler 之前创建好**(典型做法是在 `main` 里、`vTaskStartScheduler` 之前调 `xQueueCreate`),任务起来之后直接拿这个全局句柄用——这条顺序铁律和「内存在任务之前」是一脉相承的。

## 消息按值拷贝:为什么队列传的是副本,不是指针

这是整章最该带走的一个认知,也是队列和「全局变量+指针」最本质的区别。看一眼 `xQueueSend` 的签名:

```c
BaseType_t xQueueSend( QueueHandle_t xQueue,
                       const void * const pvItemToQueue,
                       TickType_t xTicksToWait );
```

第二个参数 `pvItemToQueue` 是一个 `const void *`——**指针**。但你千万不要理解成「队列里存的是这个指针」,它存的是**这块指针指向的那块数据的一个拷贝**。`xQueueSend` 内部会从 `pvItemToQueue` 这个地址出发,`memcpy` 出 `uxItemSize` 字节,塞进队列的环形缓冲区里。取出的时候对称地反着来:`xQueueReceive` 把队列里那条消息 `memcpy` 到你给的目标地址,然后把它从队列里删掉。

这个「拷进拷出」的设计有两个立竿见影的好处。第一是**数据所有权彻底解耦**:发送方投完一条消息、函数返回,那块消息原本所在的局部变量(甚至是在栈上的)随之失效也没关系,因为队列里存的是副本;接收方拿到的是另一个副本,两边的内存毫无瓜葛。你完全不用操心「发送方那块内存我什么时候还能用」——这在「传栈上局部结构体」时尤其省心。第二是**天然解决撕裂**:整块 `uxItemSize` 的拷贝是内核在临界区里一口气做完的,读者取到的永远是「一条完整的消息快照」,绝不会有「写到一半被读」的半新半旧问题。

代价也是有的:多一次 `memcpy`。对于很大的结构体,这会有开销;但绝大多数 RTOS 消息都是几十字节的小结构体(一帧采样、一条事件、一个命令),这点拷贝开销完全可以忽略。如果你确实要传一个很大的缓冲区(比如一帧图像),正经做法不是把队列的 `uxItemSize` 设成几十万,而是「队列里只传一个指针或索引,真正的大块内存另用别的方式管理」——但这就把「完整性保证」又还给你自己了,要配合互斥量或[资源管理](../08_resources/)那章的手段,不在本章范围。

理解了「按值拷贝」,你就明白为什么队列 API 都要你传地址、而不是传值了:`xQueueSend(q, &frame, ...)` 里那个 `&frame`,是告诉内核「请从这块地址开始拷 `sizeof(frame)` 字节」,frame 本身不被传进去。后面 demo 里我们会看到,sensor 任务往一个**栈上的局部结构体**里填好字段,直接 `xQueueSend` 投出去,函数返回,栈帧一弹,那块内存就没了——而 display 任务照样能完整读到那一帧,这就是按值拷贝在保护你。

## xQueueSend 与队列满:塞不进去怎么办

`xQueueSend` 的第三个参数 `xTicksToWait` 决定了「队列满时怎么办」。它的取值有三档语义,对应三种不同的工程取舍。

传 `portMAX_DELAY` 是「满了就死等」:调用任务会进 blocked,挂在「等这个队列有空间」的等待链表上,直到有消费者取走一条、腾出空位,再被唤醒完成投递。这保证了「消息绝不丢」,但代价是生产者可能被无限期卡住——如果消费者挂了或太慢,生产者就永远回不来。

传一个有限的 tick 数(比如 `pdMS_TO_TICKS(100)`)是「最多等这么久」:队列满就先 blocked 等这么久,等不到空位就返回 `errQUEUE_FULL`(也就是 `pdFALSE`),任务能继续干别的。这给了生产者一条「超时降级」的退路,生产者可以根据返回值决定是丢弃、是重试、还是报警。

传 `0` 是「满了立刻返回」:不阻塞、一次都不等,满了当场返回 `errQUEUE_FULL`。这适合「生产者自己更重要、绝不能被消费者拖住」的场景——比如一个高频采样任务,宁可丢一条消息,也不能被一个慢吞吞的日志消费者卡住节拍。

返回值你必须看:`pdPASS`(成功投递)或 `errQUEUE_FULL`(满了没投进去)。新手最常见的坑是**不看返回值、默默丢消息还不知道**——队列满了、`xQueueSend` 返回失败、消息就这么没了,你却以为它投成功了,事后查「为什么 display 少了一帧」查到天荒地老。本章的独立 demo 里,Sender 投递后会检查返回值,满了会明明白白打一行 `QUEUE FULL (dropped)`,就是这个意思。

还有一个和队列满「语义相反」的特殊投递 API 值得单独提:`xQueueOverwrite`。它只能用在**容量为 1** 的队列上,行为是「满了不报错、不阻塞,直接丢掉最旧的那条、写入新的」。它把队列当成一个**单槽的「最新值寄存器」**来用——你永远只关心「最新值」,旧的不重要、积压也不重要。dashboard 增量里 sensor 把采样发给 display 用的就是它,理由后面讲。这和「事件流/日志流」要的「一帧不丢」是两种相反的语义,选哪个完全看你的数据是「最新值重要」还是「每一条都重要」。

## xQueueReceive 与阻塞读:本章最值钱的能力

如果说 `xQueueSend` 的阻塞还只是个附带功能,那 `xQueueReceive` 的阻塞就是队列存在的核心理由。它的签名和 `xQueueSend` 几乎对称:

```c
BaseType_t xQueueReceive( QueueHandle_t xQueue,
                          void * const pvBuffer,
                          TickType_t xTicksToWait );
```

它从队列头取一条消息,`memcpy` 到 `pvBuffer` 指向的那块内存里(所以你要保证那块内存至少有 `uxItemSize` 字节,别给个不够大的缓冲区),然后从队列里删掉这条。返回值 `pdPASS` 是「取到了」,`pdFALSE`(也就是 `errQUEUE_EMPTY`)是「超时了还没取到」。

真正的主角是第三个参数 `xTicksToWait`,它和 [任务管理](../04_tasks/) 那章讲的状态机直接挂钩。当你在**空队列**上 `xQueueReceive` 时,任务不会傻等(busy-wait 占着 CPU),而是被挂进 **blocked 状态**,同时被登记到「等这个队列有数据」的等待链表上。在这段时间里它**完全不占 CPU**,调度器把它当空气,把 CPU 让给别的任务。一旦有生产者往队列里 `xQueueSend` 一条,内核会顺手把等待的接收任务唤醒(移回 ready),于是接收任务几乎立刻就能取到这条数据。这就是「事件驱动」:接收任务不是定时去问「有了吗」,而是「数据来了我才醒」。

这件事为什么值钱?对比一下就清楚了。上一章的 display 任务靠 `vTaskDelay(1000)` 盲等,每隔 1 秒去看一眼全局变量——既不及时(sensor 在两次查看之间采了好几帧,display 可能跳帧),又浪费(没数据的时候它照样每秒醒一次空转)。换成队列的阻塞读,display 在空队列上 `xQueueReceive(..., portMAX_DELAY)` 死等,sensor 一投递它就被叫醒,既做到「数据一来就处理」的近实时,又做到「没数据时零 CPU 占用」。这一升一降,就是队列把「同步」这件事从你手里接过去之后的直接收益。

`xTicksToWait` 的取值和 `xQueueSend` 一一对应:`portMAX_DELAY` 是死等(等不到永远不返回,适合「这条消息我非收不可」);一个有限的 tick 数是「最多等这么久,等不到就超时返回」,这正是本章独立 demo 要专门演的一幕;`0` 是「立刻返回,队列空就当场 `errQUEUE_EMPTY`」,适合「顺手看一眼、没有就干别的」的非阻塞轮询。`pdMS_TO_TICKS(ms)` 这个宏把毫秒换算成 tick,我们在 [任务管理](../04_tasks/) 已经反复用过它了。

这里有个新手特别容易混的点:**「队列空」不是错误,是正常状态**。一个接收任务大部分时间都在空队列上阻塞,这是设计如此、不是出了问题;你看到 `xQueueReceive` 超时返回 `errQUEUE_EMPTY`,也不是「队列坏了」,只是「这段时间没人投递」。区分「超时(正常)」和「真的出了问题」靠的是返回值和你的业务逻辑,别一看到非 `pdPASS` 就当 bug。

# 任务通知的机制、API 与开销

> 任务通知这一章的第一篇。这一篇结束时,你会彻底理解任务通知「塞进 TCB 的私人信箱」这个机制、四个核心 API 怎么调、五种 eAction 各对应什么语义、什么场景该用它、以及它比信号量/队列/事件组到底轻在哪快在哪。下一篇 [独立 demo](./02-standalone-demo.md) 把「能携带一个 32 位值」这件事演给你看,链回 [本章导航](./) 看全貌。

## 这章解决什么问题

走到这一章,我们的同步原语工具箱已经相当齐全了:队列传「一份数据」、二值/计数信号量传「一个事件」、互斥量保护「一份共享资源」、事件组传「一组位的组合」。看起来覆盖面已经够广了,可你要是真上手写一阵子,会发现有一类特别常见、特别朴素的需求,这几样原语用起来都显得「重」——**两个任务之间、单点、一对一、顺带还想塞一点点数据**。比如「通知采集任务马上再采一帧」「通知显示任务该刷新了」「通知控制任务把工作模式从普通切到加速」。这种通信说白了就是「一个任务戳另一个任务一下,可能还要带一句话」,它不需要队列那一整套缓冲和拷贝、不需要事件组那一排位、甚至不需要一把独立的信号量对象——你只是想戳一下而已。

任务通知(Task Notification)就是 FreeRTOS 给这类「轻量单点通信」专门造的原语,它也是这套教程里我们要讲的最后一个、却可能是日常代码里用得最多的同步手段。它的核心想法非常省事:**不再另起一个同步对象,而是直接把「一个 32 位的通知值 + 一个通知状态」塞进每个任务的任务控制块(TCB)里**。换句话说,每个任务天生就自带一个「私人信箱」,谁拿到它的句柄谁就能往里写,不需要 `xQueueCreate`、`xSemaphoreCreateBinary`、`xEventGroupCreate` 这些「创建」步骤——因为信箱是任务自带的、不用建。这一省,省掉的是一个完整的同步对象(一个结构体 + 一条等待链表 + 一根名字串),换来的就是更低的 RAM 占用和更短的唤醒路径。官方的说法是任务通知「比二值信号量快大约 45%」(具体数字随平台变,但量级是真的),在 RAM 吃紧、又需要频繁点对点通信的场景下,这点点省下来的开销和延迟是实打实的收益。

这一章我们要把任务通知讲透,重点会落在它最有卖点、也最容易被忽略的一个特性上——**通知值能携带一个 32 位的数据**。这正是它和二值信号量最本质的差别:信号量 `give` 一下就是一下,带不了任何东西;任务通知 `xTaskNotify` 时可以顺手塞一个 32 位值进去(动作码、一个参数、甚至一组按位的标志都行),接收方取通知时把这个值一起取出来。我们在 demo 里会演一个控制源通知工作任务「切换工作模式」的场景,把「带数据的任务通知」和「做不到带数据的信号量」放在一起对比,你会直观看到信号量版本被迫拆成「信号量 + 一个全局变量」两条通道、而任务通知一行就搞定。

## 任务通知的机制:塞进 TCB 的私人信箱

要理解任务通知为什么轻、又为什么是「单点、一对一」的,得先看清它的机制。前几章每个原语——队列、信号量、互斥量、事件组——都是一个**独立的对象**:你 `create` 它,内核给你分配一块结构体(`Queue_t`、`SemaphoreHandle_t` 背后的 `Queue_t`、`EventGroup_t`),这块结构体里挂着一条「等待这个对象的任务」链表。发送方往对象里写、接收方在对象上等,「写」和「等」是通过**对象**这个中间人撮合的。这套机制的好处是解耦——发送方和接收方不需要互相认识,谁有句柄谁就能用;代价是每个对象都占一块 RAM、唤醒时要遍历链表、信号量本质上还是借队列实现的(多一层)。

任务通知走了完全不同的路子。它**没有独立的对象**,那个「通知值」和「通知状态」直接是任务 TCB 里的两个字段:一个 `uint32_t ulNotifyValue` 存着 32 位的通知值,一个状态字段标记这个通知「有没有人发过、发过的有没有被取走」。这意味着:

第一,**任务通知是定向的、一对一的**。`xTaskNotify` 的第一个参数就是**目标任务句柄**——你必须明确告诉它「发给谁」。一个任务的通知值只有持有它句柄的人能写、只有它自己能读,不存在「一个信号量被多个任务 take」那种共享语义。这看似是限制,但对绝大多数「A 任务戳 B 任务」的场景来说,定向反而是更贴合需求的:你本来就知道要戳的是谁。

第二,**任务通知不另占对象 RAM**。因为信箱就在 TCB 里,你不需要 `create` 任何东西,任务一被 `xTaskCreate` 出来,它的通知值和状态就跟着 TCB 一起存在了。对比一下:一把二值信号量要占一个 `StaticSemaphore_t`(几十字节)+ 名字串;一个队列更多。任务通知这部分开销是零(开销早就算在 TCB 那两个字段里了,不因为你用不用而变)。

第三,**通知状态有三种**:`not waiting`(任务没在等通知)、`waiting`(任务正阻塞等通知)、`received`(有通知到了、任务还没取走)。这个状态机决定了「通知先到还是等待先到」都能正确处理:如果接收任务还没开始 `wait`、发送方就 `xTaskNotify` 了,通知会被「记着」(状态变 `received`),等接收任务后来 `wait` 时立刻就返回、不会错过——这叫「通知不丢失」;反之接收任务先 `wait` 了,发送方一来就把它唤醒。这一点和二值信号量的行为一致(信号量也能记住一次 give),但和「事件位」不同(事件位 set 了就一直在、等谁都看得到)。

顺带说一个边界:任务通知是「一个任务一个通知值」,所以它天然是**单发点对点**的——一个发送方戳一个接收方,接收方一次只能从一个通知值里取「一个东西」。如果有两个发送方同时戳同一个接收任务、而且想带不同的数据,后发的会覆盖先发的(取决于 `eAction`,下面讲),你不能像队列那样「两个消息都排队等着」。所以任务通知**不适合「多发送方往一个接收方灌一堆消息」的场景**,那个场景老老实实用队列。它最对口的还是「一个控制者给一个工作者下指令」这种 1:1 的关系。

## 四个核心 API:Give/Take 的轻量版和带值版

任务通知的 API 分成两组:一组是「无值」的,直接对应二值信号量的 give/take,适合「我就想戳你一下、不带数据」的场景;一组是「带值」的,能往通知值里塞一个 32 位数据,这是任务通知区别于信号量的核心能力。我们把它们一组组过。

先看「无值」组,这是和二值信号量一一对应的轻量替代。`xTaskNotifyGive(xTaskToNotify)` 给目标任务发一个通知:它把通知值 `+1`、把状态置为「已通知」。你看它没有「值」参数,本质就是个「+1」的快捷写法——它等价于 `xTaskNotify(xTask, 0, eIncrement)`(下面会讲 `eIncrement`)。配合它取通知的是 `ulTaskNotifyTake(xClearOnExit, xTicksToWait)`:在工作任务自己里调,阻塞等待通知,返回值是当前的**通知值**。它的两个参数里,`xClearOnExit` 决定取走后怎么处理通知值——`pdTRUE` 是「取走就清零」(适合「每次一个事件」的语义),`pdFALSE` 是「只把通知值减 1」(适合「积压计数」的语义,比如连续 `xTaskNotifyGive` 三次、`ulTaskNotifyTake(pdFALSE, ...)` 能 take 出 3);`xTicksToWait` 是阻塞超时,`portMAX_DELAY` 是死等。这套 `xTaskNotifyGive` / `ulTaskNotifyTake` 的组合,就是把「ISR/任务给二值信号量、处理任务 take 二值信号量」的写法,换成了更快更省的「任务版」——功能上一模一样,只是少了那把信号量对象。

再看「带值」组,这才是任务通知的看家本领。`xTaskNotify(xTaskToNotify, ulValue, eAction)` 是通用发通知函数:它给目标任务发通知,同时带一个 32 位 `ulValue`,并用 `eAction` 指定「这个 `ulValue` 怎么和通知值合并」。`eAction` 有五个取值,每个对应一种「通知值怎么变」的语义,这是任务通知灵活性的来源,我们挨个说:

`eSetBits`——把通知值「按位或」上 `ulValue`(`ulNotifyValue |= ulValue`)。这种模式下任务通知就在扮演一个**轻量事件组**的角色:发送方 set 某几个位,接收方收到后读哪几个位被 set 了。比起真正的事件组,它省了一个 `EventGroup_t` 对象,代价是只能给**一个**目标任务发(事件组能广播给所有等待者)。

`eIncrement`——把通知值「加 1」(`ulNotifyValue += 1`),忽略 `ulValue`。这就是 `xTaskNotifyGive` 的底层动作,适合「计数」语义:连续 notify 几次、通知值就累加几次,接收方 `ulTaskNotifyTake(pdFALSE, ...)` 逐个减 1。这其实是**轻量计数信号量**的样子。

`eSetValueWithOverwrite`——把通知值「直接覆盖」成 `ulValue`(`ulNotifyValue = ulValue`)。这是本章 demo 主用的动作——把通知值当「动作码 / 最新指令」用,后到的覆盖先到的,接收方永远拿到「最新值」。这种「最新值覆盖」语义特别适合控制类通信:控制源连发两条指令,工作任务只关心最新的那条,旧的自然丢掉。

`eSetValueWithoutOverwrite`——同样是「设成 `ulValue`」,但**如果目标任务还有上一个没取走的通知,就不覆盖、直接返回失败**(`pdFAIL`)。这适合「每条消息都不能丢」的场景:你要确保发送方知道「上一次还没被消费、这次没塞进去」,从而能重试或采取别的策略。它和 `eSetValueWithOverwrite` 的取舍,本质就是「最新值优先(可丢旧的)」还是「不丢任何一个(可能塞不进去)」。

`eNoAction`——只发通知、不动通知值。纯「戳一下」语义,连 `+1` 都不做,适合「我只想知道有没有事件发生、不关心次数也不关心数据」。

配合 `xTaskNotify` 取通知的是 `xTaskNotifyWait(ulBitsToClearOnEntry, ulBitsToClearOnExit, pulNotificationValue, xTicksToWait)`,它是「带值组」的取通知函数,比 `ulTaskNotifyTake` 更精细。`ulBitsToClearOnEntry` 是「开始等待前,先把通知值的哪几位清掉」(通常给 0,不清);`ulBitsToClearOnExit` 是「成功取到通知、返回前,把通知值的哪几位清掉」(想全清给 `0xFFFFFFFF`,想不清给 0);`pulNotificationValue` 是出参,把返回**那一刻**的通知值拷给你(注意是清位之前的值);`xTicksToWait` 还是超时。这套「entry 清位 / exit 清位 / 出参读值」的精细控制,让你既能当事件组用(按位清)、也能当信号量用(全清)、也能当「带数据的指令信箱」用(读值不清)。

你可能会问:这么多 `eAction`、这么多清位选项,到底什么时候用哪组?有个简单的判断法——**如果你只是想「戳一下、不关心数据」,就用 `xTaskNotifyGive` + `ulTaskNotifyTake(pdTRUE, ...)`,它就是二值/计数信号量的轻量替代,写起来最短、读起来最直白**;**如果你想让通知带一个值(动作码、参数、模式),就用 `xTaskNotify(xTask, value, eSetValueWithOverwrite)` + `ulTaskNotifyTake(pdTRUE, ...)`**;**如果你想让通知当一组按位标志用,就用 `eSetBits` + `xTaskNotifyWait` 按位清**。本章 demo 用的是带值组里的 `eSetValueWithOverwrite`。

## 适用场景:什么时候该用任务通知

讲完机制和 API,我们把「任务通知到底什么时候用」这道选择题说透,因为它正是任务通知最大的价值所在。任务通知最对口的场景可以浓缩成一句话:**单点、一对一、要快、要省**。展开说就是「一个明确的发送方戳一个明确的接收方、通信频率高或者 RAM 紧张、而且你不需要广播、不需要多发送方排队灌消息」。把这几个条件对上,你就能放心地用任务通知替代更重的原语。

具体到和各个原语的替代关系,任务通知能顶替它们中「单点一对一」那一部分的工作。替代二值信号量:`xTaskNotifyGive` + `ulTaskNotifyTake(pdTRUE, ...)` 在功能上等价于 `xSemaphoreGive` + `xSemaphoreTake`,但省了一整个信号量对象、还更快——只要你的「事件通知」是「一个发送方戳一个接收方」(而不是「多个任务都能 give 这把信号量」),用任务通知就划算。替代计数信号量:`ulTaskNotifyTake(pdFALSE, ...)` 配 `eIncrement`,通知值就是计数,适合「统计事件积压」;但注意任务通知的计数是**单发送方**的,多发送方得用真计数信号量。替代事件组(单接收方):`eSetBits` 让任务通知当一组位用,接收方 `xEventGroupWaitBits` 换成 `xTaskNotifyWait` 按位等;省一个 `EventGroup_t`,但只能有一个接收方(事件组能广播给所有等待者)。甚至能替代长度为 1 的队列:如果你只是想给一个任务传「最新值」、不在乎中间被覆盖丢掉,`xTaskNotify(xTask, value, eSetValueWithOverwrite)` 完美顶替「容量 1、overwrite 语义」的队列,而且快得多——本章 dashboard 的「模式切换」正是这个用法。

那么任务通知**不适合**什么场景?同样要讲清楚边界,不然容易误用。第一,**不适合「多发送方 → 一个接收方」**:因为只有一个通知值,多个发送方同时戳会互相覆盖、丢消息,这个场景老老实实用队列(队列会排队保存所有消息)。第二,**不适合「一个发送方 → 多个接收方」(广播)**:通知是定向给一个任务的,你想广播得给每个接收任务各发一次、或者干脆用事件组(事件组天生广播)。第三,**不适合「需要缓冲一串消息」**:通知值只有一个,放不下「消息队列」那一串东西,要缓冲用队列。第四,**任务通知不能像队列那样「中转」**:它必须是「直接发给最终消费者」,你不能「一个任务 take 出来再 give 给另一个任务」做接力(信号量/队列可以接力,任务通知的值没有「give 出去」这个动作)。

把这些「适合」和「不适合」摆在一起,你会发现任务通知的定位非常清晰:它是**点对点轻量通信**的尖兵,不是通用通信工具。在仪表盘、传感器采集这类「一个控制器调度几个工作线程」的嵌入式应用里,这种点对点的指令通信随处可见,所以任务通知往往是你写得最多的那一类原语。真要传一串数据(传感器采样流)还是用队列,真要等一组事件还是用事件组,真要保护共享资源还是用互斥量——任务通知不抢这些原语的地盘,它只把「戳一下、带句话」这块最朴素的活儿揽下来,做得最省。

## 轻在哪、快在哪:一次彻底的开销对比

光说「轻量、更快」太抽象,我们把它和信号量、队列、事件组做一个对照,看看「轻」「快」到底轻在哪、快在哪,这样你选型时心里有数。先看 RAM:一把二值信号量,如果开静态分配(`configSUPPORT_STATIC_ALLOCATION=1`),要占一个 `StaticSemaphore_t`(在 FreeRTOS 里这其实就是个 `Queue_t` 加些字段,几十字节量级)+ 你给它的名字串;动态分配的话还要从堆里切一块。一个队列开销更大,`Queue_t` 本身 + 一块 `长度 × 元素大小` 的消息存储区。一个事件组占一个 `EventGroup_t`(含那 24 位 + 等待链表头)。**任务通知这部分开销是零**——通知值和状态是 TCB 里本来就有的两个字段,你用不用它都在那,不因使用而多花一个字节。所以在「我只需要戳一下」的场景里,任务通知能省下一个完整的同步对象,这在 RAM 只有几 KB 的小 MCU 上是实打实的收益。

再看执行开销(速度)。二值信号量的 give/take 走的是队列那一套代码路径:`xSemaphoreGive` 内部是 `xQueueGenericSend`、`xSemaphoreTake` 内部是 `xQueueGenericReceive`,要进出临界区、要操作队列的链表(把等待任务从队列的等待链表摘下来挂回就绪链表)、要做一堆条件判断。事件组的 set/wait 也要遍历等待链表、检查每个等待者的条件。**任务通知的路径短得多**:它直接操作目标任务 TCB 里那两个字段、把目标任务从它自己的阻塞状态里唤醒,没有「中间对象」、没有「等待链表遍历」(因为只有一个等待者)。少了这些步骤,执行时间自然短一截——官方测下来典型平台上是「比二值信号量快约 45%」。当然这个数字别太较真,具体看 MCU 和编译器优化,但「更快」的量级是确凿的。

这里要插一句关于 host 模拟的诚实交代:上面这套「更省 RAM、更快」的对比,**在我们的 POSIX host 模拟上你感觉不到**。原因是 host 模拟的「任务」是一个 pthread、每个任务栈都是 `PTHREAD_STACK_MIN`(16KB)起,整套 TCB 和 pthread 的开销比真 MCU 大几个数量级,「省一个信号量对象」相对这点开销微不足道;而且 host 上没有真实时性,「快 45%」那点纳秒级差异在 PC 上根本测不出来。所以本章我们**演示的是任务通知的用法和它「能携带数据」的特性**,不是去跑分比快慢。这套「更省更快」的结论是从真 MCU 的体量推出来的、搬到真硬件上完全成立——这正是我们在教学边界章声明过的:host 模拟教机制,不教性能数字。

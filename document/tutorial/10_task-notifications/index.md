# 任务通知

## 这章解决什么问题

走到这一章,我们的同步原语工具箱已经相当齐全:队列传「一份数据」、信号量传「一个事件」、互斥量保护「一份资源」、事件组传「一组位」。但有一类特别常见、特别朴素的需求,这几样原语用起来都显得「重」——**两个任务之间、单点、一对一、顺带还想塞一点点数据**,比如「通知采集任务马上再采一帧」「通知控制任务把工作模式从普通切到加速」。任务通知(Task Notification)就是 FreeRTOS 给这类「轻量单点通信」专门造的原语:不再另起同步对象,而是**把一个 32 位通知值 + 一个通知状态直接塞进每个任务的 TCB**,任务天生自带「私人信箱」,谁有句柄谁就能往里写、不用 `create`。它比二值信号量省一整个对象、还更快(官方称典型平台快约 45%),最有卖点的是那个 32 位通知值**能携带数据**——这是信号量结构上做不到的。

## TL;DR:关键结论

| 维度 | 结论 |
|------|------|
| 核心机制 | 32 位通知值 + 通知状态直接长在 TCB 里,**不另起同步对象**、天生定向(发给指定任务)、单点一对一 |
| 省在哪 | 不占对象 RAM(开销早算在 TCB 那两个字段里)、唤醒路径短(不遍历等待链表) |
| API 分两组 | 无值组 `xTaskNotifyGive`/`ulTaskNotifyTake` 顶替二值/计数信号量;带值组 `xTaskNotify(...,eAction)`/`xTaskNotifyWait` 能塞 32 位数据 |
| 五种 eAction | `eSetBits`(轻量事件组)、`eIncrement`(轻量计数信号量)、`eSetValueWithOverwrite`(最新值指令信箱)、`eSetValueWithoutOverwrite`(不丢消息信箱)、`eNoAction`(纯戳一下) |
| 最该带走的 | **通知值能携带一个 32 位数据**——信号量 give 一下就是一下,带不了码;任务通知「通知即数据」,消掉信号量版本「信号量+全局变量」的带外通道及其竞态 |
| 什么时候用 | **单点、一对一、要快、要省 → 用它**;多发送方灌消息/要广播/要缓冲一串 → 老实用队列、事件组、信号量 |
| host 上的诚实交代 | 「更省更快」在 POSIX host 模拟上感觉不到(pthread+16KB 栈开销压倒一切、PC 无真实时性),演示的是用法和「带数据」特性;结论从真 MCU 体量推出,搬到真硬件完全成立 |

## 关于踩坑

本章在 host 模拟上演示的是任务通知的**用法和「带数据」特性**,不是跑分比快慢——「更省 RAM、更快」那套结论是从真 MCU 体量推出来的、host 上感觉不到(详见 [机制、API 与开销](./01-concept.md) 末尾的诚实交代)。关于「host 模拟 vs 真 MCU 的系统性行为差异」收在 [仿真坑点](../../pitfalls/),建议和本章对照读。
